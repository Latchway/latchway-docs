<Warning>
  This generic direct-component protocol is a pre-release target contract, not
  a supported version 1 client capability.
  Apple rejects App Attest key generation in iOS app extensions. The Swift and
  React Native iOS version 1 clients therefore do not expose Action/SSO direct
  step-up. Widget, Share, Action, and SSO extensions remain delegated-only.
</Warning>

The draft wire contract contains generic component challenge and exchange
routes. They are reserved for a platform and component type that can actually
produce independently verified evidence for its own component key. A root
assertion cannot be relabeled as component attestation.

Step-up preserves the component identity while recording composite
`delegated_direct_attested` provenance. It does not copy the root key, adopt
the root refresh chain, or erase the parent and delegation references that
show how the component began with delegated trust.

At the protocol level, a capable component would use its existing DPoP-bound
access token to create a one-use version-2 challenge, produce App Attest
evidence from its own bundle and key, and exchange it for a rotated component
session family. The challenge binds the installation family, component,
Component Definition, component key, DPoP thumbprint, platform, and step-up
purpose.

No current version 1 SDK claims a usable producer for this transition. Apple
documents an extension exception for eligible watchOS apps, but the current
Swift SDK has no watchOS direct-step-up surface. A containing Swift or React
Native application cannot prove an iOS extension bundle on the extension's
behalf. Android component clients also report direct attestation as
unsupported.

The referenced component App Attest policy is configured as `preferred` so it
cannot become an ambiguous initial-session alternative. Once the component
calls the step-up challenge/exchange endpoints, direct evidence is mandatory
and any missing, mismatched, expired, replayed, or invalid assertion fails
closed.

## Conditions for any future supported producer

- The platform verifier binds evidence to the component's application identity and key.
- Policy permits direct evidence for the component type.
- Existing delegated-only sessions are revoked and a new component session family is issued.
- Dashboard and diagnostics show composite provenance without raw evidence.
- Root or family revocation continues to apply under documented policy.
- A failed or replayed exchange cannot affect the parent or sibling components.

Until a concrete SDK/platform producer satisfies those conditions and protected
physical evidence exists, `delegated_direct_attested` remains a compatible
server/wire state rather than a supported iOS extension capability. Repository
fixtures and caller-supplied success flags do not satisfy this gate.
