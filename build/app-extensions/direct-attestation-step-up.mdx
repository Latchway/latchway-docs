---
title: "Step up to direct attestation"
description: "Plan the transition from delegated trust to direct component evidence without reusing the root key or session."
---

<Warning>
  Direct-attestation step-up for Client Components is source-implemented but
  pre-release. The Swift and React Native iOS source candidates expose the
  Action/SSO flow; no release may claim physical proof until the exact signed
  candidate completes the protected device workflow.
</Warning>

An eligible component can add independently verified platform evidence only by
completing the attestation flow for its own component key when that platform
and component type support it. A root assertion cannot be relabeled as
component attestation.

Step-up preserves the component identity while recording composite
`delegated_direct_attested` provenance. It does not copy the root key, adopt
the root refresh chain, or erase the parent and delegation references that
show how the component began with delegated trust.

The component uses its existing DPoP-bound access token to create a one-use
version-2 challenge, asks App Attest for an assertion from the extension's own
bundle and key, and exchanges it for a rotated component session family. The
challenge binds the installation family, component, Component Definition,
component key, DPoP thumbprint, platform, and step-up purpose.

This API is intentionally extension-process-only. A containing React Native
application cannot prove an extension bundle on the extension's behalf. The
React Native component client is limited to an iOS extension process and uses
the `react_native_ios` runtime; the native Swift client uses `ios`. Android
component clients report direct attestation as unsupported in version 1.

The referenced component App Attest policy is configured as `preferred` so it
cannot become an ambiguous initial-session alternative. Once the component
calls the step-up challenge/exchange endpoints, direct evidence is mandatory
and any missing, mismatched, expired, replayed, or invalid assertion fails
closed.

## Acceptance conditions

- The platform verifier binds evidence to the component's application identity and key.
- Policy permits direct evidence for the component type.
- Existing delegated-only sessions are revoked and a new component session family is issued.
- Dashboard and diagnostics show composite provenance without raw evidence.
- Root or family revocation continues to apply under documented policy.
- A failed or replayed exchange cannot affect the parent or sibling components.

The protected physical-device run must separately observe the signed host,
Widget, Share, and Action identities; independent component key and session
identifiers; the version-2 binding and trust transition; concrete sibling
denial; and no-host, background, termination, and no-user-presence behavior.
Repository fixtures and caller-supplied success flags do not satisfy this gate.
