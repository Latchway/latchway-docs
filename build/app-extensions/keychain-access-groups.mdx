---
title: "Configure Keychain access groups"
description: "Separate component private material while using narrowly scoped Keychain and App Group entitlements for app-extension provisioning."
---

<Warning>
  These identifiers and APIs describe the pre-release source candidate. No
  released SDK package or protected physical-device proof exists yet; bind the
  final values to the exact signed profiles instead of copying placeholders.
</Warning>

Give the containing application a private root access group, then give each
Client Component an independent shared group, key record, and refresh chain. A
shared Keychain access group must not become a bucket through which the
containing app and extensions reuse one private key or rotating refresh token.

For one extension component, keep the private app-ID group first in the
containing application's entitlement and add the component-specific group
after it:

```xml
<key>keychain-access-groups</key>
<array>
  <string>$(AppIdentifierPrefix)com.example.myapp</string>
  <string>$(AppIdentifierPrefix)com.example.myapp.intent</string>
</array>
```

The extension target includes only its component-specific group. Use
`$(AppIdentifierPrefix)` only in signed entitlements. At runtime, pass fully
resolved values returned by the Apple signing coordinates; unresolved build
settings fail closed.

Pass the private root group and the complete explicit shared-group list to both
the root client and App Attest provider:

```swift
let rootGroup = "ABCDE12345.com.example.myapp"
let sharedGroups = ["ABCDE12345.com.example.myapp.intent"]

let appAttest = LatchwayAppAttestProvider(
    applicationID: applicationID,
    environment: "production",
    rootKeychainAccessGroup: rootGroup,
    legacySharedKeychainAccessGroups: sharedGroups
)
let configuration = LatchwayConfiguration(
    baseURL: gateway,
    applicationID: applicationID,
    environment: "production",
    rootKeychainAccessGroup: rootGroup,
    legacySharedKeychainAccessGroups: sharedGroups,
    attestationProvider: appAttest
)
```

Pass the component's exact resolved group to its component configuration:

```swift
let intentComponent = LatchwayComponentConfiguration.appIntent(
    definitionID: "assistant_intent",
    keychainAccessGroup: "ABCDE12345.com.example.myapp.intent",
    requestedFeatures: ["assistant"]
)
```

The containing app needs the component group so it can create and provision
that component's key. The extension uses the same group to open only its own
key and session. Give every sibling extension a different group, include only
its own group in that sibling, and keep the containing app's private root group
and App Attest entitlement out of all extension targets.

The SDK proves that the configured private root group is the signed default. It
then scans the explicit shared groups only at known Latchway root-record
coordinates. A stale root record created under an earlier shared-first
entitlement fails with `rootKeychainMigrationRequired`; version 1 does not
silently read, move, or delete it.

Use an App Group only for non-secret provisioning data that the final SDK
explicitly documents. Server challenges, public-key identifiers, bounded
delegation envelopes, and status hints may be shareable if the final protocol
permits them. Private keys, identity tokens, access tokens, refresh tokens, raw
attestation objects, and upstream credentials are not.

## Verification checklist

- Confirm every target has the intended application identifier and entitlement.
- Confirm the root target's private app-ID group is first and matches the
  runtime `rootKeychainAccessGroup` exactly.
- Confirm the containing app and intended extension resolve the same component
  group, while every sibling resolves a distinct group.
- Confirm a component cannot read another component's private-key record.
- Confirm a cross-application or cross-environment envelope fails closed.
- Confirm sign-out clears or invalidates all prior-user provisioning state.
- Confirm diagnostics name the missing entitlement without printing a secret.
