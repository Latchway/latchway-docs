---
title: "Configure Keychain access groups"
description: "Separate component private material while using narrowly scoped Keychain and App Group entitlements for app-extension provisioning."
---

<Warning>
  These identifiers and APIs describe the pre-release source candidate. No
  released SDK package or protected physical-device proof exists yet; bind the
  final values to the exact signed profiles instead of copying placeholders.
</Warning>

Give each Client Component an independent key record and refresh chain. A
shared Keychain access group must not become a bucket through which the
containing app and extensions reuse one private key or rotating refresh token.

For one extension component, add the same component-specific group to the
containing app and that extension target:

```xml
<key>keychain-access-groups</key>
<array>
  <string>$(AppIdentifierPrefix)com.example.myapp.intent</string>
</array>
```

Use `$(AppIdentifierPrefix)` only in the signed entitlement. At runtime, pass
the fully resolved value returned by your Apple signing coordinate, such as
`ABCDE12345.com.example.myapp.intent`:

```swift
let intentComponent = LatchwayComponentConfiguration.appIntent(
    definitionID: "assistant_intent",
    keychainAccessGroup: "ABCDE12345.com.example.myapp.intent",
    requestedFeatures: ["assistant"]
)
```

The containing app needs the group so it can create and provision that
component's key. The extension uses the same group to open only its own key and
session. Give every sibling extension a different group, include only its own
group in that sibling, and keep the containing app's root App Attest entitlement
out of all extension targets. Passing the unresolved build-setting expression
to the runtime fails closed.

Use an App Group only for non-secret provisioning data that the final SDK
explicitly documents. Server challenges, public-key identifiers, bounded
delegation envelopes, and status hints may be shareable if the final protocol
permits them. Private keys, identity tokens, access tokens, refresh tokens, raw
attestation objects, and upstream credentials are not.

## Verification checklist

- Confirm every target has the intended application identifier and entitlement.
- Confirm the containing app and intended extension resolve the same component
  group, while every sibling resolves a distinct group.
- Confirm a component cannot read another component's private-key record.
- Confirm a cross-application or cross-environment envelope fails closed.
- Confirm sign-out clears or invalidates all prior-user provisioning state.
- Confirm diagnostics name the missing entitlement without printing a secret.
