## What changed

Server 1.1.1 fixes identity renewal after session issuance with schema 31.
The same-account verifier keeps credentials, original issuance/expiry,
attestation and quotas unchanged. The 1.1.0 contract and wire 3 are unchanged;
use 1.1.1 for supplied identity rather than the first 1.1.0 image.

iOS 1.2.0 and Android 1.1.0 add shared native accounts, application-supplied
tokens, same-account refresh and offline logout. React Native 1.2.0 is the
published matching integration release. Neither
native nor React Native needs a Firebase dependency or native authentication
bootstrap for the new API. Applications still own token refresh, provider
logout notification and account-specific UI/tool cleanup.

Shared native/RN mode requires an explicit `sharedNativeCallers` policy on the
native host. Upgrading does not widen an application's enabled platforms or
remove required attestation. Caller attribution is observational, not a second
quota owner. See [React Native authentication](/clients/react-native/authentication).

### Earlier releases

Server 1.0.4 enables bounded Chat function tools under trusted input, total-token
and input-priced cost quotas. Local schemas and complete call/result history
are included in exact-body accounting. Auth, required attestation, model
selection and quotas remain in place. See [Chat tools](/clients/react-native/framework-integrations#chat-function-tools-and-quotas).

React Native 1.1.3 declares React Native `>=0.74 <1` and React `^18.2` or `^19` host
peers. This peer-range update is independent of the server's tool fix; peer
ranges do not claim every host/framework combination has been device-tested.

Server 1.0.3 permits one directly App Attest-verified native/RN iOS main-app
root pair to share a bundle identifier, or one directly Play Integrity-verified
native/RN Android app-root pair to share a package. Each platform still needs
an explicit component definition and required attestation policy. Exact-platform
root selection, Firebase/other user authentication and quotas are unchanged.
Unconfigured platforms are not enabled automatically.

React Native 1.1.2 fixes the optional/example URL bootstrap so exact Responses
and Chat Completions paths survive React Native's incomplete built-in URL.
Recopy application-owned runtime files as well as upgrading npm. Its required
runtime dependencies remain the shared client and a private streams fallback;
its locked native dependencies remain iOS/Android 1.0.0. See
[framework setup](/clients/react-native/framework-integrations).

The standalone iOS 1.1.0 Foundation Models adapter requires OS 27 and server
1.0.2+ for expanded tools, schemas and generation options. The server cannot
bound remote/opaque state, encrypted reasoning or image attachments with its
local text-byte accounting method. This is not unrestricted multimodal or
every-model support. See the
[iOS integration guide](https://github.com/Latchway/latchway-ios-sdk/blob/v1.1.0/Documentation/FoundationModels.md).

## Upgrade and rollback

Contract 1.1.0 and wire 3 are current; compatible legacy wire-1/2 routes remain
supported. Server 1.1.1 requires schema 31. Back up PostgreSQL and preserve the
database URL, public origin, encryption/signing configuration and image digest.
Stop the old gateway, run the matching new image's migration, then start that
image and confirm readiness reports schema 31.

Migrations are forward-only and readiness requires an exact schema match.
Server 1.1.0/schema 30 is not an application-only rollback after migration 31.
Roll forward or restore the pre-migration database backup with its compatible
image. Do not edit the migration ledger or identity timestamps to force an old
binary to start.

Upgrade the gateway before activating shared native/RN identities. Before
rolling back to an older server, activate compatible revisions without those
shared identifiers in every affected environment. An older runtime rejects
them; changing the image first can prevent configuration loading.

For application setup, start with [React Native installation](/clients/react-native/installation),
[iOS signing](/clients/react-native/ios-native-setup) and
[Android Play setup](/clients/react-native/android-native-setup).
The React Native podspec comes with npm; it does not need its own CocoaPods
Trunk publication.

## Evidence and limits

Server 1.1.1 passes the complete isolated-PostgreSQL Go suite, targeted race
tests, static analysis, advancing-clock identity-renewal regression and
transactional migration rollback/upgrade checks. Its released contract archive
is byte-identical to 1.1.0. These are server checks, not physical Android or
extension acceptance.

A development-signed physical iOS 1.2.0 run exercised Firebase identity, real
App Attest, supplied-token update and streaming chat against server 1.1.1. This
does not establish Apple distribution, another application's signing, Android
Play Integrity or extension execution.

A registry-only React Native example completed one ordinary LangChain model
call on a physical iPhone against server 1.1.1, using the existing Firebase
login and App Attest. It used the published React Native SDK 1.2.0, JavaScript
client 1.1.0, LangChain adapter 1.1.0 and native iOS SDK 1.2.0 from CocoaPods,
without Metro. This single-turn run invoked no tools; it does not establish
multi-turn tool use, the full framework matrix, Android, extensions or Apple
distribution.

Server 1.0.4 passes the full Go suite, targeted race tests and authenticated
PostgreSQL tool-loop tests with JSON/streaming responses and durable quota
settlement. These use synthetic providers, not fresh physical-device evidence.

Earlier release baselines passed the full server Go package suite and Console
production build, React Native runtime regressions, 103 SDK unit tests, types,
lint, code generation, both
platform Metro bundles, native-boundary checks and deterministic package
inspection. The full historical `pnpm check` still fails in release-policy
tests referring to CI workflows removed under the maintainer's earlier decision.
Those failures are not relabeled as passes, and no replacement CI gate was added.

A compatible private DigitalOcean Compose deployment passed health/readiness and
native/RN iOS/Android configuration validation and allow/deny simulations.
Credential-level Play Integrity OAuth succeeded; rejecting a deliberately invalid
decoder token is not a real device verdict. The public release does not
automatically upgrade an existing private deployment.

Prior disposable iOS examples demonstrated Firebase authentication, App Attest,
native key possession, streaming and multi-turn tools against compatible private
gateways. Those observations do not certify the exact current public package/image
combination, another application's signing, or Android.

<Warning>
  Real Play-distributed Android verification, production Apple distribution,
  extension execution, the cloud deployment matrix, multi-replica resilience,
  load/failure certification and independent security review remain separate
  evidence. Publication through the maintainer-approved simple workflows does
  not establish the original strict A-to-Z release qualification.
</Warning>

Generated SDK bundles identify exact documentation source commits, which may
be documentation-only follow-ups to immutable SDK release tags. Compatibility
tables retain their separately versioned conformance evidence. Neither is
rewritten to claim new physical-device or provider acceptance. A synchronized
Mintlify source repository is not a production-hosting receipt.
