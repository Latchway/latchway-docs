## What changed

Server 1.0.3 permits one directly App Attest-verified native/RN iOS main-app
root pair to share a bundle identifier, or one directly Play Integrity-verified
native/RN Android app-root pair to share a package. Each platform still needs
an explicit component definition and required attestation policy. Exact-platform
root selection, Firebase/other user authentication and quotas are unchanged.
Unconfigured platforms are not enabled automatically.

React Native 1.1.2 fixes the optional/example URL bootstrap so exact Responses
and Chat Completions paths survive React Native's incomplete built-in URL.
Recopy application-owned runtime files as well as upgrading npm. Its required
runtime dependencies remain the shared client and a private streams fallback;
its locked native dependencies remain iOS/Android 1.0.0. See
[framework setup](/clients/react-native/framework-integrations).

The standalone iOS 1.1.0 Foundation Models adapter requires OS 27 and server
1.0.2+ for expanded tools, schemas and generation options. The server cannot
bound remote/opaque state, encrypted reasoning or image attachments with its
local text-byte accounting method. This is not unrestricted multimodal or
every-model support. See the
[iOS integration guide](https://github.com/Latchway/latchway-ios-sdk/blob/v1.1.0/Documentation/FoundationModels.md).

## Upgrade and rollback

Contract 1.0.0 and wire 2 remain current, with compatible legacy wire-1 grants
supported. Database schema remains 29; 1.0.3 adds no migration. Keep the database
URL, public origin and encryption master key.

Upgrade the gateway before activating shared native/RN identities. Before
rolling back to an older server, activate compatible revisions without those
shared identifiers in every affected environment. An older runtime rejects
them; changing the image first can prevent configuration loading.

For application setup, start with [React Native installation](/clients/react-native/installation),
[iOS signing](/clients/react-native/ios-native-setup) and
[Android Play setup](/clients/react-native/android-native-setup).
The React Native podspec comes with npm; it does not need its own CocoaPods
Trunk publication.

## Evidence and limits

The full server Go package suite and Console production build pass. React Native
runtime regressions, 103 SDK unit tests, types, lint, code generation, both
platform Metro bundles, native-boundary checks and deterministic package
inspection pass. Its full historical `pnpm check` still fails in release-policy
tests referring to CI workflows removed under the maintainer's earlier decision.
Those failures are not relabeled as passes, and no replacement CI gate was added.

A compatible private DigitalOcean Compose deployment passed health/readiness and
native/RN iOS/Android configuration validation and allow/deny simulations.
Credential-level Play Integrity OAuth succeeded; rejecting a deliberately invalid
decoder token is not a real device verdict. The public release does not
automatically upgrade an existing private deployment.

Prior disposable iOS examples demonstrated Firebase authentication, App Attest,
native key possession, streaming and multi-turn tools against compatible private
gateways. Those observations do not certify the exact current public package/image
combination, another application's signing, or Android.

<Warning>
  Real Play-distributed Android verification, production Apple distribution,
  extension execution, the cloud deployment matrix, multi-replica resilience,
  load/failure certification and independent security review remain separate
  evidence. Publication through the maintainer-approved simple workflows does
  not establish the original strict A-to-Z release qualification.
</Warning>

Frozen generated SDK bundles and compatibility tables identify their historical
source checkpoint. They are not rewritten to claim new device or provider
evidence. Use the versioned release notes and guides above for current package
installation; use those generated records only for the coverage they actually
describe. A synchronized Mintlify source repository is not a production-hosting
receipt.
