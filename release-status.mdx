## What changed

Server 1.1.5 adds structured operator warnings for failed App Attest and
Google Play Integrity verification. Closed reasons, processing stages and
safe request correlation help distinguish configuration, binding, evidence
and provider-service failures. App Attest phases and known Google decode
HTTP status categories are retained without exposing raw errors, credentials,
evidence, identity claims or provider bodies.

The warnings cover native/RN verification and direct App Attest component
step-up. They do not change client responses, verifier policy, quotas or the
accepted-attestation ledger. Logs follow the deployment's retention policy;
old failed verdicts cannot be reconstructed retroactively. See
[attestation failure logs](/operations/telemetry-and-jobs#attestation-failure-logs).

### Previous releases

Server 1.1.4 preserves safe request validation and selected attestation guidance,
distinguishes impossible request bounds from replenishable quotas, and retains
known retry timing. Temporary infrastructure errors no longer imply session
revocation. Failed or incomplete streams terminate abnormally after settlement;
they are not successful answers or permission to replay. Raw provider bodies,
credentials and private scope identifiers are not exposed.

JavaScript client 1.1.1, iOS 2.0.1, Android 1.2.2 and React Native 2.0.1 preserve
the existing diagnostic fields across SDK and native bridge boundaries. Custom
fetch callers must inspect unsuccessful responses with the SDK's Problem decoder;
reading only the HTTP status discards useful guidance. See
[React Native errors](/clients/react-native/error-handling),
[iOS errors](/clients/ios/error-handling),
[Android errors](/clients/android/error-handling) and
[Web errors](/clients/web/errors).
The wire contract, error code registry, schema, identity and attestation policy
are unchanged. Publishing this patch does not upgrade an existing deployment.

Server 1.1.3 adds `appAttest.environment: any` for accepting either verified
Apple environment and a Development-only opt-in for Google Play testing
responses. Google testing evidence stays `debug`; Production rejects it.
Distribution categories, identity, request binding and quotas remain separate.
Every configuration revision change requires fresh mobile evidence before
session renewal. Publishing or installing this release does not change existing
application policy. See [App Attest](/clients/ios/app-attest) and
[Play Integrity](/clients/android/play-integrity).

This release also delegates standard Google authentication and cryptographic
operations to maintained libraries while retaining the gateway's strict input,
endpoint and trust checks. Schema 33, client contract 1.1.0 and wire 3 are
unchanged; the additive Admin/configuration bundle is 1.1.2.

Server 1.1.2 introduced schema 33 and evidence-based accounting for confirmed
pre-generation provider rejection. Unknown consumption stays conservative;
historical usage is not refunded or reclassified by upgrading. Server 1.1.1
fixed same-account identity renewal after session issuance. Use the current
server for supplied identity rather than the first 1.1.0 image.

iOS 1.2.0 and Android 1.1.0 add shared native accounts, application-supplied
tokens, same-account refresh and offline logout. React Native 1.2.0 is the
published matching integration release. Neither
native nor React Native needs a Firebase dependency or native authentication
bootstrap for the new API. iOS/RN 1.3.0 and Android 1.2.0 add app-level
`signOut()` to handle current-account logout, pending identity work and interrupted
cleanup. Applications still own token refresh, provider logout notification and
account-specific UI/tool cleanup.

Shared native/RN mode requires an explicit `sharedNativeCallers` policy on the
native host. Upgrading does not widen an application's enabled platforms or
remove required attestation. Caller attribution is observational, not a second
quota owner. See [React Native authentication](/clients/react-native/authentication).

### Earlier releases

Server 1.0.4 enables bounded Chat function tools under trusted input, total-token
and input-priced cost quotas. Local schemas and complete call/result history
are included in exact-body accounting. Auth, required attestation, model
selection and quotas remain in place. See [Chat tools](/clients/react-native/framework-integrations#chat-function-tools-and-quotas).

React Native 1.1.3 declares React Native `>=0.74 <1` and React `^18.2` or `^19` host
peers. This peer-range update is independent of the server's tool fix; peer
ranges do not claim every host/framework combination has been device-tested.

Server 1.0.3 permits one directly App Attest-verified native/RN iOS main-app
root pair to share a bundle identifier, or one directly Play Integrity-verified
native/RN Android app-root pair to share a package. Each platform still needs
an explicit component definition and required attestation policy. Exact-platform
root selection, Firebase/other user authentication and quotas are unchanged.
Unconfigured platforms are not enabled automatically.

React Native 1.1.2 fixes the optional/example URL bootstrap so exact Responses
and Chat Completions paths survive React Native's incomplete built-in URL.
Recopy application-owned runtime files as well as upgrading npm. Its required
runtime dependencies remain the shared client and a private streams fallback;
its locked native dependencies remain iOS/Android 1.0.0. See
[framework setup](/clients/react-native/framework-integrations).

The standalone iOS 1.1.0 Foundation Models adapter requires OS 27 and server
1.0.2+ for expanded tools, schemas and generation options. The server cannot
bound remote/opaque state, encrypted reasoning or image attachments with its
local text-byte accounting method. This is not unrestricted multimodal or
every-model support. See the
[iOS integration guide](https://github.com/Latchway/latchway-ios-sdk/blob/v1.1.0/Documentation/FoundationModels.md).

## Upgrade and rollback

iOS 2.0.0 and its paired React Native 2.0.0 integration remove legacy root
constructors, callback authorities, credential adoption and migration APIs.
Use shared `configure` and application-supplied identity. They do not migrate
older SDK storage automatically; reinstalling does not guarantee Keychain
erasure. Current private-Keychain, account/generation, attestation and retirement
checks remain enforced, including deny-only extension safety guards.

Rebuild and distribute the native app together with the new JavaScript bridge;
an OTA-only JavaScript update cannot upgrade its ABI or native libraries.
Use one iOS SDK copy when native and React Native share a host. App-level
`signOut()` remains available, including pending sign-in and interrupted cleanup.
Captured-account `logout()` is still the safe choice for delayed old-account
work. Neither operation signs out the external identity provider or resets quota.

Contract 1.1.0 and wire 3 are current; compatible legacy wire-1/2 routes remain
supported. Server 1.1.5 requires schema 33. Back up PostgreSQL and preserve the
database URL, public origin, encryption/signing configuration and image digest.
Stop the old gateway, run the matching new image's migration, then start that
image and confirm readiness reports schema 33. Existing schema-33 deployments
need no additional SQL migration or application-policy activation for 1.1.5.

Migrations are forward-only and readiness requires an exact schema match.
Do not start a schema-30/31 binary against a schema-33 database.
Roll forward or restore the pre-migration database backup with its compatible
image. Do not edit the migration ledger or identity timestamps to force an old
binary to start. A 1.1.3-to-1.1.2 image rollback is schema-compatible, but first
restore singular Apple acceptance and disable Google testing if those new
policies have been activated. Never relax Production to work around a failed
development test.

Upgrade the gateway before activating shared native/RN identities. Before
rolling back to an older server, activate compatible revisions without those
shared identifiers in every affected environment. An older runtime rejects
them; changing the image first can prevent configuration loading.

For application setup, start with [React Native installation](/clients/react-native/installation),
[iOS signing](/clients/react-native/ios-native-setup) and
[Android Play setup](/clients/react-native/android-native-setup).
The React Native podspec comes with npm; it does not need its own CocoaPods
Trunk publication.

## Evidence and limits

Server 1.1.5 passes the complete isolated-PostgreSQL Go suite, static analysis,
affected-package race tests and canonical documentation checks. Tests exercise
Google HTTP 400/403 classification, preflight/configuration failures, native/RN
request correlation, App Attest phases and sensitive-data redaction. The
published GHCR image includes Linux amd64 and arm64, and its contract bundle
remains byte-identical to 1.1.2. A digest-pinned private VPS rollout passed all
seven readiness checks without changing either environment's policy, schema
or log rotation. These are release and operational receipts, not fresh
physical-device or live-provider proof.

Server 1.1.4 passes the complete isolated-PostgreSQL Go suite, static analysis,
targeted race checks and real-HTTP partial-stream regression tests. Its contract
bundle is byte-identical to 1.1.2; the published GHCR image includes Linux amd64
and arm64. No private VPS rollout was performed for this patch.

JavaScript client 1.1.1 passes 150 tests. Android 1.2.2 passes 223 tests with one
live-only skip, build/lint and independent API-34 consumers. All five public Maven
modules and their 240 versioned files match the signed release bundle.
iOS 2.0.1 passes 118
affected tests, 20 Foundation Models tests, the example build and a separate

One pre-existing cancellation/logout timing test also fails on unchanged 2.0.0;

The public CocoaPods specification, source archive and SwiftPM tag are verified.

React Native 2.0.1 passes 261 unit, 13 runtime, 12 iOS bridge, 13 Android bridge
