The Cloudflare deployment keeps authentication, attestation, routing, quota,
secrets, and upstream access inside the standard Latchway container. A small
Worker selects one of four container-backed Durable Objects and forwards the
request and response without buffering.

<Warning>
  The stable `1.0.0` image has not been published yet. Do not replace the
  placeholders on this page until the release page supplies the signed GHCR
  index and `linux/amd64` child digests.
</Warning>

When release coordinates exist, complete
[release-image verification](/operations/verify-release-image) before mirroring
the `linux/amd64` child.

## Why the image is mirrored

Cloudflare Containers supports Cloudflare Registry, Docker Hub, Amazon ECR,
and Google Artifact Registry as prebuilt-image sources. It does not pull from
GHCR directly. The release process therefore keeps
`ghcr.io/latchway/latchway@sha256:...` as the canonical signed image and copies
its verified `linux/amd64` child into `registry.cloudflare.com` without
rebuilding it.

The mirror is acceptable only when its OCI config digest and ordered layer
descriptors match the canonical amd64 child. A matching version label or a
successful start is not sufficient. See Cloudflare's
[image management guide](https://developers.cloudflare.com/containers/guides/image-management/)
for the supported registry flow.

## Prerequisites

- a Cloudflare account with Containers enabled;
- Node.js 24 and pnpm 10;
- the repository-pinned Wrangler `4.127.1` release;
- Docker Buildx, `jq`, and `sha256sum` for the one-time GHCR pull, mirror push,
  and manifest comparison;
- an active Cloudflare DNS zone for the final hostname, with no existing CNAME
  at that hostname;
- a publicly reachable PostgreSQL 15 or newer endpoint with TLS; and
- the verified canonical OCI index and `linux/amd64` child digests.

Cloudflare Containers executes `linux/amd64`. Pull the child digest, not the
multi-architecture index, before mirroring.

## Capacity, cost, and scaling limits

The checked-in deployment is application-scaled rather than a general-purpose
platform autoscaler:

| Setting | Checked-in behavior | Operating consequence |
| --- | --- | --- |
| Container type | `standard-1`: 0.5 vCPU, 4 GiB memory, 8 GB ephemeral disk | The image must fit the instance disk; larger types change the cost and capacity model |
| Application ceiling | Four named container-backed Durable Objects | The Worker rejects a configured count above four; increasing it requires a reviewed source and test change |
| Request routing | Random selection among the four fixed identities | Routing is not locality-aware or load-aware, and each selected stopped instance can cold-start |
| Idle lifecycle | Ten-minute sleep timer for each container | Instances 1–3 can sleep after inactivity and restart in another location |
| Required worker | A one-minute Cron Trigger calls `instance-0` | Each successful trigger reactivates or keeps one combined API/worker container warm; the platform does not guarantee uninterrupted runtime |
| Database pool | Five connections per identity | The four-identity application ceiling reserves up to 20 application connections |

Cloudflare bills Containers for provisioned memory and disk while an instance
is active, active CPU time, and network egress. Workers, Durable Objects, and
observability have separate usage. The deployment requires a Workers Paid plan;
continual reactivation by the one-minute trigger normally creates an idle-cost
floor even when no client request arrives. Cloudflare does not guarantee that
an instance runs for any fixed duration; review the [Containers FAQ](https://developers.cloudflare.com/containers/faq/)
and current [Containers pricing](https://developers.cloudflare.com/containers/platform/pricing/),
[instance and image limits](https://developers.cloudflare.com/containers/platform/limits/),
and [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
before deployment. Provider rates and account quotas are not pinned here.

## Placement, residency, and database exposure

The release configuration has no placement constraint. Cloudflare can start a
container near available capacity, and a restarted identity can run in a
different location. The current random router does not choose the identity
nearest PostgreSQL. Measure database latency and cross-region egress under the
expected client distribution.

The current template connects directly from the container to an
internet-reachable PostgreSQL endpoint. Require a provider-trusted CA and
`sslmode=verify-full`, use a database role limited to the Latchway database, and
apply the strongest network controls compatible with Cloudflare Container
egress. TLS does not make an unrestricted public database endpoint private.

If policy requires a jurisdiction or regional boundary, add reviewed Container
[placement constraints](https://developers.cloudflare.com/containers/concepts/placement/)
near the selected database and validate the complete data path, including logs,
upstreams, and backups. An ad hoc edit to the generated release config is
rejected and is not a residency control.

## Validate the deployment source

```bash
cd deploy/cloudflare
pnpm install --frozen-lockfile
pnpm types:check
pnpm check
pnpm deploy:dry-run
```

The checked-in `wrangler.jsonc` points to the repository Dockerfile so local
source review works. A stable deployment must use the generated release config,
which rejects mutable tags, direct GHCR references, and Dockerfile builds.
It also requires one exact, lowercase, non-wildcard Custom Domain.

## Mirror the exact amd64 child

Substitute the release-provided digest and use a temporary local tag:

```bash
export LATCHWAY_AMD64_IMAGE='ghcr.io/latchway/latchway@sha256:REPLACE_WITH_AMD64_CHILD_DIGEST'
docker pull --platform linux/amd64 "$LATCHWAY_AMD64_IMAGE"
docker tag "$LATCHWAY_AMD64_IMAGE" latchway:1.0.0-amd64
pnpm exec wrangler containers push latchway:1.0.0-amd64
```

Wrangler returns a Cloudflare Registry URI. Resolve and record that image by
digest; never put its tag-only form into the release configuration. Export the
exact URI printed by Wrangler, obtain a 15-minute pull credential, and compare
the two raw manifests:

```bash
set -Eeuo pipefail
umask 077
export LATCHWAY_CLOUDFLARE_TAG='registry.cloudflare.com/ACCOUNT_ID/latchway:1.0.0-amd64'
latchway_manifest_dir=$(mktemp -d "${TMPDIR:-/tmp}/latchway-manifests.XXXXXX")
install -d -m 0700 "$latchway_manifest_dir/docker-config"
trap 'rm -rf "$latchway_manifest_dir"' EXIT HUP INT TERM

pnpm exec wrangler containers registries credentials registry.cloudflare.com \
  --pull \
  --expiration-minutes 15 \
  --json > "$latchway_manifest_dir/cloudflare-registry-credentials.json"
latchway_registry_username=$(jq -er '.username | select(type == "string" and length > 0)' \
  "$latchway_manifest_dir/cloudflare-registry-credentials.json")
jq -er '.password | select(type == "string" and length > 0)' \
  "$latchway_manifest_dir/cloudflare-registry-credentials.json" \
  | docker --config "$latchway_manifest_dir/docker-config" \
      login registry.cloudflare.com \
      --username "$latchway_registry_username" \
      --password-stdin

docker --config "$latchway_manifest_dir/docker-config" \
  buildx imagetools inspect --raw "$LATCHWAY_AMD64_IMAGE" \
  > "$latchway_manifest_dir/canonical.json"
docker --config "$latchway_manifest_dir/docker-config" \
  buildx imagetools inspect --raw "$LATCHWAY_CLOUDFLARE_TAG" \
  > "$latchway_manifest_dir/mirror.json"

latchway_canonical_digest="sha256:$(sha256sum \
  "$latchway_manifest_dir/canonical.json" | awk '{print $1}')"
latchway_mirror_digest="sha256:$(sha256sum \
  "$latchway_manifest_dir/mirror.json" | awk '{print $1}')"
test "$latchway_canonical_digest" = "${LATCHWAY_AMD64_IMAGE##*@}"

jq -S '{config_digest:.config.digest,layers:[.layers[]|{digest,size}]}' \
  "$latchway_manifest_dir/canonical.json" \
  > "$latchway_manifest_dir/canonical-descriptors.json"
jq -S '{config_digest:.config.digest,layers:[.layers[]|{digest,size}]}' \
  "$latchway_manifest_dir/mirror.json" \
  > "$latchway_manifest_dir/mirror-descriptors.json"
cmp "$latchway_manifest_dir/canonical-descriptors.json" \
  "$latchway_manifest_dir/mirror-descriptors.json"

export LATCHWAY_CLOUDFLARE_IMAGE="${LATCHWAY_CLOUDFLARE_TAG%:*}@$latchway_mirror_digest"
rm -rf "$latchway_manifest_dir"
trap - EXIT HUP INT TERM
unset latchway_manifest_dir latchway_registry_username
```

The raw mirror-document digest becomes the immutable Cloudflare reference. The
descriptor comparison separately proves that the mirror has the canonical
config and ordered `layers[].digest` plus `layers[].size` values. Keep the
canonical index digest, canonical amd64 child digest, and Cloudflare mirror
digest in the deployment record; registries may serialize content-equivalent
manifests differently.

## Generate the immutable release config

```bash
export LATCHWAY_DOMAIN='ai.example.com'
pnpm release:config -- \
  --image "$LATCHWAY_CLOUDFLARE_IMAGE" \
  --domain "$LATCHWAY_DOMAIN"
pnpm release:dry-run
```

The generated `wrangler.release.jsonc` is ignored and mode-restricted. Review
the dry-run output and confirm the container image and exact Custom Domain are
the expected values. Cloudflare creates the DNS record and manages its
certificate when Wrangler deploys this config. Because it is a prebuilt
registry image, Docker is not required for the deployment step itself. See
Cloudflare's [Custom Domains requirements](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/#add-a-custom-domain).
Every release deploy byte-compares the ignored file with deterministic
regeneration from the reviewed source; comments, extra routes, duplicate
content, or manual edits fail closed.

## Prepare first-deploy secrets

A new Worker cannot receive required secrets in advance with `wrangler secret
put`. Prepare one protected temporary JSON file and supply it to the first
reviewed release deployment. Do not put secret values in shell arguments,
history, the repository, or Terraform state:

```bash
umask 077
latchway_secrets_file=$(mktemp "${TMPDIR:-/tmp}/latchway-wrangler-secrets.json.XXXXXX")
trap 'rm -f "$latchway_secrets_file"' EXIT
"${EDITOR:-vi}" "$latchway_secrets_file"
jq --exit-status '
  (keys | sort) == [
    "LATCHWAY_ADMIN_BOOTSTRAP_TOKEN",
    "LATCHWAY_DATABASE_URL",
    "LATCHWAY_MASTER_KEY",
    "LATCHWAY_PUBLIC_ORIGIN"
  ] and all(.[]; type == "string" and length > 0)
' "$latchway_secrets_file" >/dev/null
```

Enter a JSON object containing exactly those four keys. The file is mode
`0600`; keep the trap active until the first deployment completes. For an
existing Worker, rotate one value with `pnpm exec wrangler secret put NAME
--config wrangler.release.jsonc`. Each such mutation creates and deploys a
Worker version, so the explicit immutable-image config is a security boundary.

Requirements:

- `LATCHWAY_DATABASE_URL` uses TLS; prefer `sslmode=verify-full` with a trusted
  provider CA.
- `LATCHWAY_MASTER_KEY` decodes to exactly 32 bytes and is escrowed outside
  Cloudflare with the database recovery material.
- `LATCHWAY_PUBLIC_ORIGIN` is the exact final HTTPS origin with no path, query,
  or fragment.
- `LATCHWAY_ADMIN_BOOTSTRAP_TOKEN` is 32–2048 bytes and exists only until
  the first owner is created.

The default four instances each use a five-connection PostgreSQL pool, for 20
application connections. Reserve separate headroom for migrations,
administration, backups, and maintenance before changing either limit.

## Apply migrations

Run migrations from the canonical signed image in a controlled job with the
database secret injected by the execution environment:

```bash
set -Eeuo pipefail
latchway_migration_status=$(mktemp "${TMPDIR:-/tmp}/latchway-migration-status.XXXXXX.json")
trap 'rm -f "$latchway_migration_status"' EXIT HUP INT TERM

docker run --rm --platform linux/amd64 \
  -e LATCHWAY_DATABASE_URL \
  "$LATCHWAY_AMD64_IMAGE" \
  migrate up

docker run --rm --platform linux/amd64 \
  -e LATCHWAY_DATABASE_URL \
  "$LATCHWAY_AMD64_IMAGE" \
  --output json migrate status \
  > "$latchway_migration_status"

jq --exit-status '
  (keys | sort) == ["available", "current", "up_to_date"] and
  .up_to_date == true and .current == .available
' "$latchway_migration_status" >/dev/null
rm -f "$latchway_migration_status"
trap - EXIT HUP INT TERM
```

The assertion must pass against the same canonical amd64 child that was
mirrored. The first deployment retains
`LATCHWAY_MIGRATE_ON_START=true` as an advisory-lock-protected fallback. After
bootstrap, set it to `false` and use explicit migrations for every upgrade.

## Deploy and wait for rollout

For the first deployment, atomically create the Worker and its required secrets
with the reviewed generated config:

```bash
pnpm exec wrangler deploy \
  --config wrangler.release.jsonc \
  --secrets-file "$latchway_secrets_file"
rm -f "$latchway_secrets_file"
unset latchway_secrets_file
trap - EXIT
```

For an existing Worker whose required secrets already exist, deploy without a
secrets file:

```bash
pnpm release:deploy
pnpm exec wrangler containers list --config wrangler.release.jsonc
```

Cloudflare activates Worker code before the container rollout completes. These
steps are not transactional, so the Worker URL can be live while the new
container is still provisioning. Wait until the application and instances are
active before testing or recording the deployment. Cloudflare documents this
behavior in [Deploy Containers](https://developers.cloudflare.com/containers/guides/deploy/).

Require the active application to name the exact mirror digest, then require the
cron-targeted `instance-0` to run the active application version. Poll for at
most four minutes because Worker activation and the Container rollout are
asynchronous:

<Warning>
  Wrangler `4.127.1` returns only one provider page from `containers list
  --json`; its `--per-page` option does not change that JSON path. Use a
  dedicated deployment account whose `latchway` application is on that page,
  or replace this block with a reviewed paginated Cloudflare API check. An
  absent application blocks promotion; it does not prove rollout success or
  failure.
</Warning>

```bash
set -Eeuo pipefail
latchway_cloudflare_state=$(mktemp -d "${TMPDIR:-/tmp}/latchway-cloudflare-state.XXXXXX")
trap 'rm -rf "$latchway_cloudflare_state"' EXIT HUP INT TERM

latchway_rollout_ready=false
for _ in {1..24}; do
  pnpm exec wrangler containers list --json \
    --config wrangler.release.jsonc \
    > "$latchway_cloudflare_state/applications.json"
  latchway_application_id=$(jq -er --arg image "$LATCHWAY_CLOUDFLARE_IMAGE" '
    [ .[]
      | select(.name == "latchway" and .image == $image and
               (.state == "active" or .state == "ready"))
    ]
    | if length == 1 and (.[0].instances | type == "number") and
         .[0].instances >= 1 and (.[0].version | type == "number")
      then .[0].id
      else empty
      end
  ' "$latchway_cloudflare_state/applications.json" || true)

  if [[ "$latchway_application_id" =~ ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$ ]]; then
    latchway_application_version=$(jq -er --arg id "$latchway_application_id" '
      .[] | select(.id == $id) | .version
    ' "$latchway_cloudflare_state/applications.json")
    pnpm exec wrangler containers instances "$latchway_application_id" \
      --search instance-0 \
      --json \
      --config wrangler.release.jsonc \
      > "$latchway_cloudflare_state/instances.json"
    if jq --exit-status --argjson version "$latchway_application_version" '
      length == 1 and .[0].name == "instance-0" and
      .[0].state == "running" and .[0].version == $version
    ' "$latchway_cloudflare_state/instances.json" >/dev/null; then
      latchway_rollout_ready=true
      break
    fi
  fi
  sleep 10
done
test "$latchway_rollout_ready" = true

rm -rf "$latchway_cloudflare_state"
trap - EXIT HUP INT TERM
```

Verify both platform and forwarded probes:

```bash
curl --fail --show-error https://ai.example.com/__latchway/cloudflare/healthz
curl --fail --show-error https://ai.example.com/healthz
curl --fail --show-error https://ai.example.com/readyz
```

Then run one authenticated non-streaming request and one SSE request against
the public origin. The Worker must stream responses without buffering.

## Remove bootstrap access

After creating the first owner in the Console, generate the reviewed
post-bootstrap configuration from the same release source and image. This mode
sets `LATCHWAY_MIGRATE_ON_START` to `false` and omits the bootstrap binding
without an ad hoc tracked-source edit. Deploy it first, then delete the
now-unreferenced Worker secret.

```bash
pnpm release:config -- \
  --image "$LATCHWAY_CLOUDFLARE_IMAGE" \
  --domain "$LATCHWAY_DOMAIN" \
  --post-bootstrap
pnpm check
pnpm release:deploy
pnpm exec wrangler secret delete LATCHWAY_ADMIN_BOOTSTRAP_TOKEN --config wrangler.release.jsonc
```

The delete also deploys a Worker version. Keeping the post-bootstrap config
explicit prevents that operation from restoring the mutable development image,
startup migrations, or the removed bootstrap binding.

## Rollback and recovery

The checked-in rollout advances 10%, 50%, then 100%. Wait for completion and
prove readiness and SSE behavior at every release. Use `wrangler versions list`
to identify a previous Worker version and `wrangler rollback VERSION_ID` for an
application rollback. Cloudflare's [image-management guidance](https://developers.cloudflare.com/containers/guides/image-management/)
warns that deleting an image makes a previous Worker version that references it
fail when restored. Retain every prior mirror through the rollback window.

After rollback, export the expected previous mirror digest and rerun the bounded
application-and-instance block under
[Deploy and wait for rollout](#deploy-and-wait-for-rollout) with that value:

```bash
export LATCHWAY_CLOUDFLARE_IMAGE='registry.cloudflare.com/ACCOUNT_ID/latchway@sha256:PREVIOUS_MIRROR_DIGEST'
pnpm exec wrangler versions list --config wrangler.release.jsonc
pnpm exec wrangler rollback VERSION_ID \
  --config wrangler.release.jsonc \
  --message 'Emergency rollback to reviewed previous release'
```

Then require the exact previous mirror image, `/readyz`, an authenticated
non-streaming request, and an SSE request. Database migrations are forward-only.
Use the previous application only after isolated current-schema proof; otherwise
restore a tested backup with the matching master key.

Cloudflare documents that rollback immediately creates a 100%-traffic
deployment of the selected version and does not revert bound resources. Review
the current [Workers rollback behavior and limits](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
before invoking it.

Container disk is ephemeral. PostgreSQL remains the only authoritative
application state store. Never store recovery data inside the container or
Durable Object filesystem.

Complete [production readiness](/operations/production-readiness),
[backup and restore](/operations/backup-restore), and
[upgrades and rollback](/operations/upgrades) before promotion.

## Release evidence boundary

A successful `wrangler deploy` is deployment evidence, not release evidence.
The protected release receipt must bind the canonical signed index, canonical
amd64 child, content-equivalent mirror, active Cloudflare application and
instances, migration status, secret names without values, health/readiness,
SSE, SIGTERM replacement, and the exact immutable source coordinates.
