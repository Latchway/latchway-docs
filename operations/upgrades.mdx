Latchway migrations are transactional, advisory-lock protected, and
forward-only. Readiness requires the database's current migration version to
equal the binary's bundled available version. Application rollback needs a
verified compatible image; otherwise restore a tested pre-upgrade backup into
a fresh database.

## Preflight

Record current image digest, binary/contract version, schema, active
configuration revision, SDK versions, and worker heartbeat. Verify the new
digest's signature, provenance, SBOM, vulnerability, and license results.

Complete a fresh backup and recent isolated restore drill. Ensure PostgreSQL
connections and capacity can carry the overlap of old and new replicas.

<Warning>
  A tag alone does not establish image identity or provenance. Verify the exact
  digest and its corresponding release assets before promotion.
</Warning>

## Roll forward

1. Deploy the new image as a migration job without application traffic.
2. Run `latchway migrate status`, exactly one `latchway migrate up`, then status
   and doctor again.
3. Roll worker replicas first when release notes require new maintenance logic;
   otherwise preserve one compatible heartbeat throughout.
4. Send a small percentage of API traffic to the new digest.
5. Verify session refresh, JSON, streaming, quotas, settlement, fallback,
   metrics, logs, and traces before increasing traffic.
6. Drain old replicas for at least `LATCHWAY_SHUTDOWN_TIMEOUT`—30 seconds by
   default—and retain the previous digest through the observation window.

Do not combine schema migration, public-origin change, master-key change,
emergency signing rotation, and a large upstream configuration rewrite in one
rollout.

Rolling overlap requires both binaries to accept the current schema. When the
schema changes, use a drained maintenance transition. An unhealthy container
does not necessarily stop a reverse proxy from forwarding requests to it.

## Application rollback

Stop the rollout when readiness, latency, error rate, or correctness regresses.
The binary has no declared schema range. Before routing traffic back, run that
exact previous binary's migration status, doctor, and readiness checks against
an isolated copy of the current database. Current and bundled available
migration versions must match.
Preserve failed replica telemetry and let workers reclaim reservations; never
edit quota tables manually.

## Schema 29: Terminal-attempt validation

Migration `29` replaces only the deferred terminal-validator function body.
It consolidates validation reads while preserving check outcomes, error
precedence, legacy settlement repair, trigger timing, locks, tables, indexes,
and constraints. Historical migration `28`, wire `2`, the frozen schema-28
contract bundle, and SDK locks remain unchanged.

<Warning>
  A schema-28 binary becomes unready after migration `29`, even though the
  table layout is unchanged. It is not an application-rollback target. Do not
  rely on a ready rolling overlap of schema-28 and schema-29 replicas.
</Warning>

Rehearse the exact migration and traffic transition before deployment. For
application rollback, retain and verify a compatible schema-29 release
candidate before promoting a schema-29 stable image. Both binaries must report
current and available schema `29` and pass doctor and readiness in the
RC-to-stable-to-RC drill.

To recover schema `28`, restore a pre-29 backup/PITR point into a fresh database
and start the matching previous image with its matching master key. This is
schema recovery, not application-rollback evidence. Never delete migration
ledger rows, edit migration `28`, or relax readiness to permit an incompatible
image.

## Schema 30: Caller attribution

When deploying a server that bundles migration `30`, expect a nullable
`logical_requests.caller_sdk` column with a bounded-value check. Existing rows
remain null; quota ownership, buckets, and usage are unchanged. The migration
requires a table lock and may scan existing requests while validating the
constraint, so rehearse it against a populated isolated database.

<Warning>
  A schema-29 binary becomes unready as soon as migration `30` commits. Keeping
  its old image is not sufficient for application rollback on schema `30`.
</Warning>

For this transition:

1. Preserve the old image, matching master key, configuration revision IDs, and
   a verified pre-upgrade backup/PITR path. Test a separate schema-30-compatible
   rollback artifact before deployment.
2. Remove application traffic and drain old processes for their shutdown timeout.
   Keep the origin, database connection, TLS state, and master key unchanged.
3. Apply migration `30` in one new-image migration job using the existing valid
   environment configuration. Keep `LATCHWAY_MIGRATE_ON_START=false` on the app.
4. Inspect `latchway --output json migrate status`: require current and available
   schema `30` with `up_to_date: true`. Mismatch alone does not make this command
   exit unsuccessfully.
5. Start the compatible application and worker, inspect doctor and readiness,
   and check requests, refresh, streaming, and settlement before restoring traffic.
   Activate shared-native caller policy only in the intended environments.

An older application rebuilt to bundle migration `30` is a distinct artifact,
not the unchanged published image, and still lacks wire-3 support. Restore only
the affected environments' previous compatible configuration revisions through
the Admin API before using it. Shared-native clients fail closed on older
wire-1/2 servers; they are not automatically converted to legacy sessions.

Recovering schema `29` requires a pre-30 backup/PITR restore into a fresh database,
with the matching old image and master key. This affects every application in
the database and may lose writes after the recovery point. Never delete migration
ledger rows, manually drop the new column, or relax readiness to fake compatibility.

## Schema recovery

There are no down migrations. To undo schema state:

1. remove application traffic;
2. restore the pre-upgrade backup or PITR point into a new database;
3. start the matching previous image with the matching master key;
4. run the complete restore verification;
5. switch traffic to the recovered environment.

Deleting migration-ledger rows or hand-editing production tables is unsupported
and can break quota, audit, signing, replay, or recovery guarantees.

## PostgreSQL major upgrades

Treat a PostgreSQL major-version change as a database migration, not as an
application image update. PostgreSQL 18's official image stores versioned
clusters beneath `/var/lib/postgresql`; the checked-in release Compose template
therefore mounts that directory. A volume created with the older
`/var/lib/postgresql/data` layout must not be attached directly to PostgreSQL 18.

Before changing the pinned PostgreSQL digest, create and verify an independent
backup, use a supported major-upgrade path such as logical dump/restore or
`pg_upgrade`, restore into an isolated volume, and run the complete Latchway
migration, doctor, readiness, quota, and streaming checks. Keep the old database
and matching application digest recoverable until the observation window ends.

## Release proof

The release gate runs an authenticated distinct-ancestor candidate, the current
candidate, and then the prior application again against one isolated database.
The prior binary must report that the database's current migration version
equals its bundled available migration version and become ready after rollback.
A database restore proves schema recovery, not application rollback
compatibility.

The current version 1 evidence includes a supplemental local drill, not a
protected released-image receipt. Repeat the drill against the exact candidate
before promotion.
