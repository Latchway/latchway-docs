Latchway key classes have different lifecycles. Treating them as interchangeable
can make encrypted records unrecoverable or invalidate every mobile session.

## Environment master key

`LATCHWAY_MASTER_KEY` is a base64-encoded 32-byte root used to protect managed
secrets and gateway signing material. Version 1 has no in-place rewrap workflow.
Replacing the value is not rotation: readiness fails when durable records name
another master-key identifier.

Escrow the exact key separately from PostgreSQL. A master-key change requires a
future audited rewrap or a planned restore/migration, not an environment-variable
edit during rollout.

## Gateway signing keys

The worker owns durable signing-key rotation. New keys become active while old
public keys remain in JWKS long enough for issued access tokens and verifier
caches to expire. Monitor rotation jobs, JWKS publication, readiness, and clock
skew across replicas.

Version 1 exposes no Admin API or CLI operation to force signing-key rotation,
select a new active key, or shorten JWKS overlap. Scheduled rotation is therefore
not emergency containment. If private signing material may be disclosed,
isolate the affected environment from traffic and administrative mutation,
preserve key IDs and lifecycle timestamps, and revoke known affected user,
family, or component sessions where scope is established. Do not hand-edit
signing-key rows, delete JWKS state, or change the master key during containment.

Keep the affected environment offline until a reviewed, deployment-specific
recovery procedure or supported software change establishes a clean signing
state. Do not return traffic merely because the scheduled worker created a later
key; version 1 provides no documented live emergency-rotation guarantee.

## Identity-provider keys

Remote JWKS is cached in PostgreSQL so replicas share refresh and failure
behavior. Respect provider cache metadata and the configured stale-key safety
window. Test a real provider rollover with multiple API replicas before relying
on it in production.

Static public keys and HS256 verification secrets change through a reviewed
immutable configuration and managed-secret procedure. HS256 remains an
explicit-risk configuration because verification and signing share material.

## Upstream credentials

1. Create a new managed-secret version through the console or CLI.
2. Create and activate a configuration revision that references it.
3. Run a bounded server-owned self-test and verify production traffic.
4. Delete the old version only after reference checks permit it.
5. Recreate any scheduled self-test intentionally; schedules fail closed when
   their pinned secret version changes.

```bash
printf '%s' "$NEW_PROVIDER_KEY" | \
  latchway secret rotate sec_... --from-stdin
```

The Admin API never returns plaintext. Reconcile an indeterminate rotation by
operation ID before retrying.

## Administrator credentials

Remove `LATCHWAY_ADMIN_BOOTSTRAP_TOKEN` after the first owner is created. Reset
a compromised password through the Admin API, revoke API tokens and affected
sessions, verify current owners, and review redacted audit events. Disabling an
administrator membership revokes its organization-scoped sessions and tokens.

Include master-key escrow, signing overlap, provider rotation, identity-key
rollover, and administrator recovery in the production drill schedule.
