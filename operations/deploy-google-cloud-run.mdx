Run the Latchway image, connect PostgreSQL, and open the embedded Console. You
do not need to fork or clone the source, build an image, learn Terraform, or
configure GitHub Actions or Workload Identity Federation to operate Latchway.
The default path below uses Google Cloud Console and an existing PostgreSQL
15-or-newer database. Cloud Shell commands are included where useful.

<Warning>
  Stable `1.0.0` publication is pending. Replace
  `ghcr.io/latchway/latchway@sha256:REPLACE_WITH_RELEASE_DIGEST` only with the
  signed digest from the release record. Check [Release status](/release-status)
  and [verify the image](/operations/verify-release-image) before deploying.
  These instructions are not a claim that live GCP verification has passed.
</Warning>

## Before you start

- Select a Google Cloud project with billing enabled and a region close to the
  database. Cloud Run, the database, secrets, logs, and network traffic can all
  incur charges; this guide does not provision anything on your behalf.
- Obtain a verified public GHCR image digest with a `linux/amd64` manifest.
- Prepare a PostgreSQL 15+ database, a dedicated database user, and a connection
  URL. Use a direct connection for migrations, not a transaction-pooling URL.
- Use an operator account permitted to create Cloud Run services/jobs, service
  accounts, and secrets, grant their narrow access, and enable required APIs.
  Runtime accounts must not inherit your operator privileges.

Cloud Run accepts public GHCR images directly. An Artifact Registry remote
repository is an optional availability measure, not a prerequisite; never
rebuild the release to change registries. See Google's
[supported image sources](https://docs.cloud.google.com/run/docs/deploying).

## 1. Choose the database and public origin

### Existing PostgreSQL: fewest new resources

Use an existing PostgreSQL endpoint reachable from both the Cloud Run service
and migration job. Store a URL shaped like this in Secret Manager, not in
source control or a shell command:

```text
postgresql://latchway:URL_ENCODED_PASSWORD@DB_HOST:5432/latchway?sslmode=verify-full
```

Require certificate and hostname verification. If your provider uses a private
CA, mount its certificate into both containers and add
`sslrootcert=/etc/latchway-db-ca/ca.pem` to the URL; do not disable TLS to make
the connection work. The release image includes public CA roots. The database
user must be able to create and update the Latchway schema, but must not be a
server-wide superuser. Prefer a dedicated database with no unrelated tables.

Keep the database private where your network permits. For a public managed
endpoint, retain the provider's access controls. Cloud Run's default outbound
addresses are not fixed: a database IP allowlist requires controlled egress,
such as VPC egress and Cloud NAT. Do not open PostgreSQL to every address to
avoid setting up that network. Google's
[static outbound IP guide](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip)
describes that optional setup. Private endpoints need a matching VPC route on
both the service and job.

### Cloud SQL alternative

If you need a new database, create Cloud SQL for PostgreSQL 15+ in the same
region, create the `latchway` database/user, and enable backups and point-in-time
recovery. Choose HA and capacity deliberately; a database remains billable
without application traffic.

For Cloud SQL's managed Unix-socket connection, enable the Cloud SQL Admin API,
grant both service accounts Cloud SQL Client, and attach the same instance
under **Cloud SQL connections** on the service and migration job. Store:

```text
postgresql://latchway:URL_ENCODED_PASSWORD@/latchway?host=/cloudsql/PROJECT_ID:REGION:INSTANCE_ID&sslmode=disable
```

Here `sslmode=disable` applies only to the local Unix socket: the managed
connector encrypts and authenticates the network connection. Never use that
setting for a direct TCP URL. A public-IP Cloud SQL instance can use this
connector without an open authorized-network rule; private-IP connectivity
requires the corresponding VPC setup. Follow Google's
[Cloud Run to Cloud SQL guide](https://docs.cloud.google.com/sql/docs/postgres/connect-run)
for the chosen network and certificate mode.

### Use the built-in HTTPS URL

You do not need a custom domain or load balancer for initial setup. Choose the
short service name `latchway` and find the project number on the project's
dashboard. The initial canonical origin is:

```text
https://latchway-PROJECT_NUMBER.REGION.run.app
```

Use the project **number**, not the project ID. This predictable URL is
available when the hostname's first segment is at most 63 characters; verify
the displayed URL after deployment. Google documents the
[deterministic service URL](https://docs.cloud.google.com/run/docs/triggering/https-request).

Set `LATCHWAY_PUBLIC_ORIGIN` to this exact HTTPS origin, without a path. Use the
same origin for the Console and SDKs. Do not issue sessions on a temporary or
tagged revision URL. Moving to a custom domain later is a planned origin
change, not a cosmetic rename.

## 2. Store three values and scope their access

In **APIs & Services**, enable Cloud Run, Secret Manager, and IAM. In
**IAM & Admin → Service Accounts**, create `latchway-runtime` and
`latchway-migrator`. Do not create or download JSON keys.

In **Secret Manager**, create these secrets. Generate the master key as 32
cryptographically random bytes encoded as base64, and a separate random
bootstrap token of at least 32 characters. Save the master key in a password
manager independently of database backups. Changing it later is not rotation.

| Secret | Value | Secret Accessor grant |
| --- | --- | --- |
| `latchway-database-url` | PostgreSQL connection URL | Runtime and migrator accounts |
| `latchway-master-key` | One stable base64-encoded 32-byte key | Runtime account only |
| `latchway-admin-bootstrap-token` | Temporary first-owner setup key | Runtime account until bootstrap is removed |

Grant **Secret Manager Secret Accessor** on each named secret, not on the
whole project. Select an explicit secret version, such as `1`, for each
environment binding. If you already have different versions, substitute their
numbers in every service/job binding. Do not use `latest` for a repeatable
rollout. See Google's [secret binding guidance](https://docs.cloud.google.com/run/docs/configuring/services/secrets).

Replication and retention are separate choices: place secrets, logs, and
backups within the required residency policy. Selecting a Cloud Run region
alone does not establish data residency.

## 3. Run migrations before starting the service

In **Cloud Run → Jobs**, create `latchway-migrate` in the chosen region with the
same verified GHCR digest you will use for the service:

| Setting | Value |
| --- | --- |
| Service account | `latchway-migrator@PROJECT_ID.iam.gserviceaccount.com` |
| Container command | `/latchway` |
| Container arguments | `migrate`, `up` as separate arguments |
| Container CPU / memory | `1` vCPU / `512 MiB` |
| Tasks / parallelism / retries | `1` / `1` / `0` |
| Task timeout | `900` seconds |
| Secret environment variable | `LATCHWAY_DATABASE_URL` → `latchway-database-url`, version `1` |

For Cloud SQL or private PostgreSQL, attach the database connection/network
from step 1. A custom CA mount must also exist on this job. The job needs no
master key or administrator bootstrap token.

Execute the job and require a successful exit. Then execute it again with the
argument override `--output`, `json`, `migrate`, `status`. In that execution's
logs, require the status object to report `up_to_date: true` and equal
`current` and `available` values. Check the specific execution, not an older
success from the same job. Do not deploy on failure or delete migration-ledger
rows to force success.

Cloud Shell equivalent, after creating the identities and secrets above:

```bash
export LATCHWAY_GCP_PROJECT='PROJECT_ID'
export LATCHWAY_GCP_REGION='asia-southeast1'
export LATCHWAY_IMAGE='ghcr.io/latchway/latchway@sha256:REPLACE_WITH_RELEASE_DIGEST'
export LATCHWAY_PUBLIC_ORIGIN='https://latchway-PROJECT_NUMBER.asia-southeast1.run.app'

gcloud run jobs create latchway-migrate \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" \
  --container latchway-migrate --image "$LATCHWAY_IMAGE" \
  --service-account "latchway-migrator@$LATCHWAY_GCP_PROJECT.iam.gserviceaccount.com" \
  --command /latchway --args=migrate,up \
  --cpu 1 --memory 512Mi \
  --tasks 1 --parallelism 1 --max-retries 0 --task-timeout 900s \
  --set-secrets=LATCHWAY_DATABASE_URL=latchway-database-url:1

gcloud run jobs execute latchway-migrate \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" --wait
gcloud run jobs execute latchway-migrate \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" \
  --args=--output,json,migrate,status --wait
```

These commands assume an external TLS database reachable without extra network
flags. For the Cloud SQL socket path, add
`--set-cloudsql-instances=PROJECT_ID:REGION:INSTANCE_ID` when creating the job
and deploying the service. Add reviewed VPC settings when required. See Google's
[job configuration](https://docs.cloud.google.com/sdk/gcloud/reference/run/jobs/create)
and [execution overrides](https://docs.cloud.google.com/sdk/gcloud/reference/run/jobs/execute).

## 4. Deploy the container

In **Cloud Run → Deploy container**, choose **Deploy one revision from an
existing container image**. Enter the GHCR digest and use these settings:

| Setting | Value |
| --- | --- |
| Service name / region | `latchway` / the selected database region |
| Authentication / ingress | Allow public access / All |
| Service account | `latchway-runtime@PROJECT_ID.iam.gserviceaccount.com` |
| Billing / scaling | Instance-based billing, minimum `1`, maximum `3` service instances |
| Container command / arguments | `/latchway` / `serve`, `--role`, `all` |
| Port / CPU / memory | `8080` / `2` vCPU / `2 GiB` |
| Concurrency / request timeout | `100` / `3600` seconds |
| Startup HTTP probe | `/readyz`, port `8080`, initial delay `1s`, period `3s`, timeout `3s`, failure threshold `40` |
| Liveness HTTP probe | `/healthz`, port `8080`, period `15s`, timeout `3s`, failure threshold `3` |

Public Cloud Run ingress lets SDK requests reach Latchway; it does not grant
Latchway sessions or administrator access. Latchway applies its own identity,
attestation, DPoP, and authorization checks. Google documents the
[public access setting](https://docs.cloud.google.com/run/docs/authenticating/public).

Under **Variables and Secrets**, add the non-secret environment values:

| Variable | Value |
| --- | --- |
| `LATCHWAY_ROLE` | `all` |
| `LATCHWAY_PUBLIC_ORIGIN` | The exact `https://latchway-PROJECT_NUMBER.REGION.run.app` origin |
| `LATCHWAY_MIGRATE_ON_START` | `false` — the explicit job already migrated |
| `LATCHWAY_DB_MAX_CONNECTIONS` | `20` aggregate connections per instance |
| `LATCHWAY_DB_COMPLETION_CONNECTIONS` | `5`, reserved inside the aggregate total; regular work receives `15` |
| `LATCHWAY_SHUTDOWN_TIMEOUT` | `8s` |
| `LATCHWAY_LOG_LEVEL` | `info` |

Use **Reference a secret** for `LATCHWAY_DATABASE_URL`, `LATCHWAY_MASTER_KEY`,
and `LATCHWAY_ADMIN_BOOTSTRAP_TOKEN`, selecting their matching secrets and
numeric versions. Do not paste secret values as ordinary environment variables.
Do not set `PORT` yourself; Cloud Run supplies it from the container port.

The combined API/worker process requires CPU between requests and at least one
running instance. Request-based CPU throttling or scale-to-zero can stop
background jobs and expire the worker heartbeat. This is why this deployment
uses [instance-based billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings).
Cloud Run permits ten seconds after `SIGTERM`; the `8s` application drain fits
inside that [shutdown window](https://docs.cloud.google.com/run/docs/container-contract).

Cloud Shell equivalent for the external TLS database path:

```bash
gcloud run deploy latchway \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" \
  --container latchway --image "$LATCHWAY_IMAGE" \
  --service-account "latchway-runtime@$LATCHWAY_GCP_PROJECT.iam.gserviceaccount.com" \
  --no-invoker-iam-check --ingress all \
  --execution-environment gen2 --no-cpu-throttling --min 1 --max 3 \
  --cpu 2 --memory 2Gi --concurrency 100 --timeout 3600s --port 8080 \
  --command /latchway --args=serve,--role,all \
  --set-env-vars="LATCHWAY_ROLE=all,LATCHWAY_LOG_LEVEL=info,LATCHWAY_MIGRATE_ON_START=false,LATCHWAY_PUBLIC_ORIGIN=$LATCHWAY_PUBLIC_ORIGIN,LATCHWAY_SHUTDOWN_TIMEOUT=8s,LATCHWAY_DB_MAX_CONNECTIONS=20,LATCHWAY_DB_COMPLETION_CONNECTIONS=5" \
  --set-secrets=LATCHWAY_DATABASE_URL=latchway-database-url:1,LATCHWAY_MASTER_KEY=latchway-master-key:1,LATCHWAY_ADMIN_BOOTSTRAP_TOKEN=latchway-admin-bootstrap-token:1 \
  --startup-probe=httpGet.path=/readyz,httpGet.port=8080,initialDelaySeconds=1,periodSeconds=3,timeoutSeconds=3,failureThreshold=40 \
  --liveness-probe=httpGet.path=/healthz,httpGet.port=8080,periodSeconds=15,timeoutSeconds=3,failureThreshold=3
```

The flags are documented in the current
[`gcloud run deploy` reference](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy).
An organization policy may forbid public ingress; resolve that with the project
administrator rather than weakening the organization's policy.

## 5. Verify, create the owner, and remove the setup key

Confirm that Cloud Run displays the expected HTTPS origin, the intended ready
revision, and the configured immutable image. Require both probes to pass:

```bash
gcloud run services describe latchway \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" \
  --format='yaml(status.url,status.latestReadyRevisionName,spec.template.spec.containers[0].image)'
curl --fail --show-error "$LATCHWAY_PUBLIC_ORIGIN/healthz"
curl --fail --show-error "$LATCHWAY_PUBLIC_ORIGIN/readyz"
```

Inspect the ready revision's resolved image digest and compare it with the
verified release record, including its `linux/amd64` manifest. An image tag or a
healthy unrelated revision is not sufficient. Readiness checks PostgreSQL,
schema, active-environment configuration, the reserved quota-completion pool,
key material, and worker heartbeat.
An empty installation can be ready for owner setup; this does not prove a
client application has been configured.

Open the exact public origin in your browser. Use the bootstrap token as the
setup key and choose your own owner email and password. There is no default
administrator email or password. Complete the [Console setup](/administration/console)
and configure your identity provider, upstream secrets, features, and enabled
platforms. Provider credentials belong in Latchway's managed secrets, never in
an SDK or example application.

After the first owner exists, edit the service and remove only the
`LATCHWAY_ADMIN_BOOTSTRAP_TOKEN` secret binding. Keep the same image, database
URL, and master key; deploy and verify the new revision:

```bash
gcloud run services update latchway \
  --project "$LATCHWAY_GCP_PROJECT" --region "$LATCHWAY_GCP_REGION" \
  --remove-secrets=LATCHWAY_ADMIN_BOOTSTRAP_TOKEN
curl --fail --show-error "$LATCHWAY_PUBLIC_ORIGIN/readyz"
```

Confirm all traffic is on the post-bootstrap revision and remove any old
traffic tags before revoking the runtime account's accessor grant on that
bootstrap secret. Retire the unused secret version under your retention policy.
Do not remove database or master-key access. Verify owner login, an
authenticated client request, and an SSE response through the canonical origin.

## Limits and production decisions

- This is not a scale-to-zero profile. The always-on worker and database have
  idle costs. Check [Cloud Run pricing](https://cloud.google.com/run/pricing),
  [Cloud SQL pricing](https://cloud.google.com/sql/pricing), and your database
  provider's price before creating resources.
- At three instances and an aggregate 20 connections each, the application
  ceiling is 60 connections. The five completion connections per instance are
  inside that ceiling, leaving 45 regular and 15 completion-reserved
  connections across three instances; do not budget 60 + 15. Add migrations,
  administration, backup, maintenance, and rollout overlap, then keep the
  planned peak at or below 80% of usable PostgreSQL connections for 20%
  headroom.
  The service template and Terraform set both pool values explicitly; override
  both together rather than expecting the runtime default to recompute one.
  Cloud Run can temporarily exceed a configured maximum; treat it as a scaling
  control, not a hard database-connection guarantee. See Google's
  [maximum-instance behavior](https://docs.cloud.google.com/run/docs/configuring/max-instances).
- Requests have a [60-minute Cloud Run ceiling](https://docs.cloud.google.com/run/docs/configuring/request-timeout). Set application stream limits
  below it, reconnect SSE clients, and never enable buffering or CDN caching for
  API streams. Replacement can interrupt a stream despite graceful draining.
- The direct public endpoint also exposes `/metrics` on the same listener;
  it is not administrator-authenticated. Metrics are redacted but contain
  operational information. If they must be private, use a reviewed edge that
  restricts that path and prevents bypass through `run.app` before production
  traffic. A private database does not make this HTTP path private.
- A custom domain is optional. If one is needed, follow Google's
  [custom-domain guidance](https://docs.cloud.google.com/run/docs/mapping-custom-domains),
  configure the exact origin before issuing client sessions, and preserve SSE.
- Escrow the master key independently, enable database backups, and prove an
  isolated restore. Complete [production readiness](/operations/production-readiness)
  before treating the deployment as production-qualified.

## Upgrade without Terraform

1. Back up PostgreSQL and prove a restore with the matching master key. Verify
   the next image digest and migration compatibility before changing anything.
2. Update only the migration job to the new digest. Execute `migrate up` and
   then `--output json migrate status`; require a current status while the old
   service keeps traffic.
3. Deploy the same new digest as a named candidate revision with no traffic.
   In the Console, clear the option to serve the revision immediately, or use
   `gcloud run deploy ... --no-traffic --tag candidate`. Preserve every runtime
   setting and numeric secret version; do not restore the bootstrap binding.
4. Probe `/healthz` and `/readyz` through the candidate tag URL. Keep
   `LATCHWAY_PUBLIC_ORIGIN` on the canonical URL; do not distribute the tag URL
   as client configuration. Use an isolated staging deployment for full
   authenticated pre-promotion tests.
5. Shift traffic explicitly to the verified revision, then exercise owner
   login, a client request, and SSE at the canonical origin. Record the previous
   revision and resolved digest for the observation window.

Cloud Run supports [manual revision traffic control](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)
without Terraform. An application rollback changes traffic only; it does not
undo schema changes. The previous binary must be proven against the current
schema first. Otherwise use the tested database restore and matching master
key described in [Rollbacks](/operations/rollbacks).

## Optional: infrastructure as code and maintainer evidence

Teams that want reproducible infrastructure can use the advanced
[`deploy/cloud-run` Terraform stack](https://github.com/Latchway/latchway/tree/main/deploy/cloud-run).
It creates private PostgreSQL 18 Cloud SQL, VPC connectivity, secrets, a service,
and a migration job. Its production-oriented defaults cost more than reusing a
database: regional HA Cloud SQL, at least two VPC connector instances, and an
always-on Cloud Run instance. Review the plan and encrypted remote-state custody
before applying. Terraform is an optional operator choice, not a product
dependency or a requirement for a fork.

The project's GitHub deployment-evidence workflow, protected environments, and
keyless WIF identity are maintainer release-verification machinery. Ordinary
adopters do not need them to deploy manually. A manual deployment remains
subject to its own operating checks; it does not automatically create the
project's signed provider receipt or satisfy deferred external evidence.

The selected maintainer receipt is fixed to project `latchway`, region
`asia-southeast1`, service `latchway`, job `latchway-migrate`, and Cloud SQL
connection `latchway:asia-southeast1:latchway-postgres`. It proves public
ingress, unauthenticated Cloud Run invocation, and that exact managed connector
over the `/cloudsql/...` Unix socket. The pinned `gcloud` collector consumes
Cloud Run's v1/Knative JSON compatibility shape: the Cloud SQL connection is an
exact `run.googleapis.com/cloudsql-instances` annotation on the desired service
template, ready revision, job execution template, and created execution. It
rejects VPC annotations and any explicit volume or mount in that v1 shape.

Terraform uses Cloud Run API v2 instead. Its private-IP/VPC service and job
represent the same managed socket with a `cloudSqlInstance` volume and
`/cloudsql` volume mount. That is a separate production-oriented adopter
topology, not an alternative JSON shape accepted by the selected receipt. The
receipt identity cannot read Secret Manager payloads, so it does not attest the
database URL contents even though it verifies the pinned secret references.
