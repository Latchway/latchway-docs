React Native 1.2.0 uses the same native account backend as Swift and Kotlin.
Either native or React Native can configure first. Matching public settings
reuse one app, installation, account and session; conflicting explicit settings
fail closed.

Start with the [React Native quickstart](/clients/react-native/quickstart) for
installation and a complete request. Check [Release status](/release-status)
for registry publication and separate physical-device limits.

## Requirements

- React Native `>=0.74.0 <1.0.0`, React `^18.2.0 || ^19.0.0` and the New
  Architecture, using a compatible host pair.
- iOS 15+, iOS SDK 1.2.0, the signed private root Keychain group and App Attest.
- Android API 24+, Android SDK 1.1.0 and required Play Integrity. Libraries
  compile against API 34; the host may need a newer compile or target SDK.
- Server 1.1.1 and an explicit shared-native caller policy for the host.
- Application-owned login and current user ID tokens accepted by the gateway.

## Shared app and identity

`Latchway.configure` accepts public gateway, application, environment, identity
metadata and native security coordinates. It does not sign in. No Firebase
dependency, native Latchway auth bootstrap or embedded-mode switch is required.

Supply a current token through `app.signIn({getIdToken})` after accepted login.
Already-active native/RN callers attach with `app.makeClient()`. Initial auth
restoration uses `app.restore({getIdToken})`, which cannot undo recorded logout.
The optional `firebaseProject` helper only formats issuer/audience metadata;
it does not fetch tokens or install listeners.

ID tokens stay in native process memory, not persistent SDK storage. Supply
fresh tokens with `account.updateIdToken`. At expiry,
`identity_refresh_required` suspends protected work until a verified update.
Native may continue after JS teardown while supplied identity remains fresh
and the app has not reported a change. Restart requires application auth to
supply a token again.

See [authentication](/clients/react-native/authentication) for one-shot token
callbacks, operation cancellation and the optional provider-neutral binding.

## Logout and screen cleanup

`account.logout()` retires that captured account across native and React Native,
including offline. Old account handles cannot refresh or log out a newer user.
Logout does not revoke the whole installation, reset server-side user quota,
log out other devices or sign out your external authentication provider.

Serialize external-provider login/logout calls in application code. Every auth
surface must notify Latchway; the SDK cannot observe changes in a provider it
does not depend on. Abort old streams/tools and clear local chat history.
Screen teardown calls `client.dispose()`, not shared logout.

## Transport and replay

Native modules own key storage, attestation, DPoP signing, session refresh and
credential-bearing requests. JavaScript receives safe responses and bounded
diagnostics, never private keys, session credentials or raw attestation.

`fetchFor(feature)` binds one server-owned protocol route. Request bodies are
buffered within the 8 MiB bridge limit; server policy may impose a lower limit.
Responses stream incrementally. Redirects and cross-origin authorization are
rejected. JavaScript must not clone authenticated requests or replay uncertain
provider dispatches. Only native code decides bounded pre-dispatch recovery.

Frameworks and polyfills belong to the host app. See
[framework integrations](/clients/react-native/framework-integrations) for
LangChain setup, cancellation, tool loops and token accounting.

## Native host and extension boundaries

Follow [iOS host setup](/clients/react-native/ios-native-setup) and
[Android host setup](/clients/react-native/android-native-setup). Inspect actual
signed entitlements and Play app-signing configuration rather than guessing
identifiers. Include real legacy storage coordinates when migrating; a made-up
empty list is not a migration strategy.

The React Native extension surface remains distinct from a main-app account.
A delegated extension is not directly attested merely because its parent is.
Do not infer production App Intent or extension execution from root-app
success. Follow [app extensions](/clients/react-native/app-extensions).

## Verify the application

Exercise both configuration orders, token refresh, expiry/recovery, switching
accounts, offline logout, JS teardown, streaming and cancellation. Correlate
safe request IDs with the expected native host, caller, user, feature, trust
and quota in the Console.

A simulator, emulator, fixture or package publication is not physical
attestation evidence. Verify the exact iOS signing path and Play-distributed
Android build separately. See [device proof](/mobile/device-proof) and the
[security boundary](/concepts/security-boundary).
