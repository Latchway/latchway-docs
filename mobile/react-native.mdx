title: "React Native"
description: "Integrate the Latchway React Native SDK with native App Attest and Play Integrity bridges."
---

`@latchway/react-native` exposes one fetch-shaped API while native iOS and
Android modules own installation keys, DPoP signing, rotating session state,
and platform attestation.

## Requirements

- React Native 0.82.x with the New Architecture enabled
- iOS 15 or newer with an App Attest-capable application entitlement
- Android API 24 or newer with Play Integrity configured
- a version-compatible Latchway gateway and SDK source set

The intended `1.0.0` package has not been published. For evaluation, use an
authorized checkout of the React Native source candidate and its example
application. Do not substitute an unverified registry package.

The source example is the supported prepublication integration path because it
pins the exact JavaScript, Swift, and Android source revisions together with the
normative contract checkpoint and compatible gateway version range. It does
not pin the current gateway implementation commit. Its local native overrides
are development-only and must not appear in a published package.

<Warning>
  The example's App Intents extension is currently a signing, provisioning,
  and Keychain-entitlement fixture. It deliberately fails closed instead of
  sending a delegated Latchway request, so including or launching that target
  is not delegated-component execution evidence.
</Warning>

## Create a client

```typescript
import { createLatchwayClient } from "@latchway/react-native";

const latchway = createLatchwayClient({
  baseURL: "https://gateway.example.com",
  applicationID: "app_01J00000000000000000000000",
  environment: "production",
  getIdentityToken: async () => {
    const token = await applicationIdentity.currentToken();
    if (token === undefined) {
      throw new Error("The user must sign in before calling Latchway.");
    }
    return token;
  },
  android: {
    playIntegrityCloudProjectNumber: applicationConfiguration.googleCloudProjectNumber,
  },
  apple: {
    rootKeychainAccessGroup: applicationConfiguration.rootKeychainAccessGroup,
    legacySharedKeychainAccessGroups:
      applicationConfiguration.extensionSharedKeychainAccessGroups,
  },
});

const response = await latchway.fetch("/v1/chat/completions", {
  method: "POST",
  latchwayFeature: "habit_assistant",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    model: "assistant-default",
    messages: [{ role: "user", content: "Plan tomorrow" }],
  }),
});
```

`applicationID` is generated by the Admin API. A package name, bundle ID,
display name, or slug is not interchangeable with it.

## Lifecycle and replay behavior

Call `dispose()` when the owning application scope is destroyed. Secure
installation state remains available to later instances. `refresh()` rotates
session credentials explicitly; `revokeCurrentInstallation()` destroys the
server installation and local secure state.

JavaScript never clones or replays a request. Native may retry at most once for
an exact canonical pre-dispatch `session_expired` or `dpop_nonce_required`
response when the body was already buffered within the 8 MiB bridge limit.
Streaming or otherwise non-replayable request bodies are never retried.
Redirects and cross-origin authorization are rejected.

The client also exposes `quota(feature)`, `refresh()`,
`revokeCurrentInstallation()`, and `dispose()`. `diagnostics()` combines the
native SDK/platform compatibility state with a protected server snapshot. It
can report secure key-storage category, attestation support and accepted
provider/trust, session state and expiry, refresh availability where the native
surface exposes it, installation status, server version, and safe request/error
IDs.

Diagnostics never returns access or refresh tokens, DPoP proofs or private
keys, raw attestation evidence, identity subjects or claims, or provider
credentials. The server validates the active DPoP-bound session, consumes a
fresh proof replay key, and rejects an SDK kind that does not match the stored
`react_native_ios` or `react_native_android` installation.

## Native host setup

On iOS, install JavaScript dependencies, run CocoaPods from the host app, and
enable App Attest for the exact application identifier. Configure
`apple.rootKeychainAccessGroup` with the fully resolved private app-ID group
that appears first in the root application's signed entitlement. List every
explicit extension-shared group in
`apple.legacySharedKeychainAccessGroups`; never pass an unresolved
`$(AppIdentifierPrefix)` expression. The bridge passes the same groups to the
native App Attest provider and root client, keeping Keychain, Secure Enclave,
session, and attested-key state inside the iOS SDK. A stale root record in an
explicit shared group fails closed and requires an explicit migration.

On Android, compile against API 37 for the source candidate, configure the
numeric Play cloud project in `android.playIntegrityCloudProjectNumber`, and
include the locked `dev.latchway` native modules. The integrity token stays
inside the native bridge.

React Native 0.82 uses the New Architecture. Equivalent JavaScript clients in
one runtime share the native security scope; conflicting security configuration
for that active scope fails closed.

## Production attestation

React Native delegates to the native SDKs:

- iOS uses an App Attest entitlement and a supported physical device.
- Android uses the configured cloud project and an exact signed application
  installed through the configured Google Play track.

Simulator, emulator, fixture, and sideloaded-debug success are development
signals only. See [Physical-device proof](/mobile/device-proof) and
[Security boundary](/concepts/security-boundary).
