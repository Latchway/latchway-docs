Production attestation is an external deployment gate. Repository fixtures,
simulators, emulators, debug evidence, and locally sideloaded builds prove
development behavior only.

<Warning>
  Version 1 history has a development-signed physical iOS root-application
  observation. The current React Native source adds a Debug native App Intent
  path that has not yet been physically invoked. No source has completed a
  protected Apple distribution-derived App Attest run or a physical Play
  Integrity run. Do not describe the candidate as release-qualified or
  production-deployed until those exact-candidate receipts exist.
</Warning>

## Current development-signed iOS observation

A real iPad running iPadOS 26.5 exercised React Native commit
`6de46e1c7264e1d45cdd31174e4ea040a8c24acf` in Debug configuration with
automatic Apple Development signing and bundle `dev.latchway`. The gateway
accepted Apple production App Attest trust at validation category `3` and
bundle version `1`. Registration and a subsequent assertion reused the same
App Attest key through a temporary ngrok tunnel, the current source gateway,
and Firebase identity. The server persisted the assertion counter and hash.

The same run passed Secure Enclave DPoP, upstream non-streaming and streaming
requests, quota, a typed `403 component_feature_not_granted` response, native
bridge behavior, and cleanup. It did not use Apple Distribution, ad hoc,
TestFlight, or App Store distribution; it was not bound to a protected
immutable candidate; and it did not execute the delegated extension runtime.
It is useful device evidence for development, but it does not close the release
gate.

## iOS and React Native iOS

Prepare all of the following:

- an App Attest-capable physical iPhone or iPad;
- a registered App ID with App Attest enabled;
- matching Team ID, bundle ID, signing certificate, and provisioning profile;
- the App Attest environment selected consistently in the entitlement,
  application, gateway policy, and test runner;
- the exact distribution-derived validation category: `3` for development
  signing, `2` for TestFlight, `4` for App Store, or `5` for ad hoc/enterprise;
- the exact `CFBundleVersion`/`CURRENT_PROJECT_VERSION` build number, not the
  marketing version, in the gateway bundle-version allowlist;
- a production-distributed application identity token;
- the exact candidate gateway image and synchronized iOS or React Native SDK.

Production policy should disallow software key fallback. The evidence run must
observe Secure Enclave-backed installation material, real App Attest
registration/assertion, the expected normalized trust, a DPoP-authorized
request, and terminal revocation behavior.

The protected run must also pin and independently observe the signed containing
app and every included Widget, Share, Action, App Intents, or other extension
binary; separate component key and session identifiers; a concrete
sibling-denial response; and no-host, background, termination, and
no-user-presence behavior. These iOS extensions remain delegated-only. Apple
rejects App Attest key generation in iOS app extensions, and the containing
app's assertion cannot substitute for or be relabeled as extension evidence.
Being signed and embedded proves target inclusion only; it does not prove the
extension executed a delegated request.

## Android and React Native Android

Prepare all of the following:

- a supported physical Android device;
- the exact release package name and signing certificate digest;
- the Play Integrity API and numeric Google Cloud project;
- a signed build uploaded to an internal, closed, or production Google Play
  track and installed from Google Play;
- licensing and device-integrity policy matching the gateway environment;
- the exact candidate gateway image and synchronized Android or React Native
  SDK.

The app passes the server challenge as Play Integrity `requestHash`. JavaScript
and application code must never construct, read, or persist the integrity token.
Exercise the hardware-backed or StrongBox policy variants required by your
device matrix.

## Minimum retained evidence

For native iOS, native Android, React Native iOS, and React Native Android,
retain a redacted report tied to the exact candidate that covers:

1. installation creation and normalized hardware/application trust;
2. session reuse, identity expiry, and reauthentication;
3. DPoP proof replay and tamper rejection;
4. server nonce handling and refresh-token rotation;
5. quota inspection and a bounded streaming request;
6. diagnostics without tokens, keys, proofs, or attestation objects;
7. revocation followed by a fresh installation enrollment.

The report should name application release, device and OS, gateway image
digest, contract bundle checksum, SDK versions, and request IDs. It must not
contain identity/session credentials, DPoP material, signing files, provider
credentials, or raw attestation evidence.

The release finalizer accepts only reports from the protected physical-device
workflow for the same candidate. A handwritten success summary is not a
substitute.

## Runner custody

Use an ephemeral or on-demand physical-device runner dedicated to one
candidate evidence run. It must not retain an organization token, package or
registry credential, cloud OIDC authority, signing export, provisioning file,
attestation object, or device proof after the run. Candidate checkout and test
execution must occur without long-lived administrative credentials; any
bootstrap grant should be short-lived, one-use, and bound to the repository,
workflow run, candidate commit, and expected audience.

Always destroy or reimage the runner after capture, revoke the bootstrap grant,
and verify cleanup even when a test fails or is cancelled. A persistent runner
that has executed candidate code is not a safe place to perform release
mutation or hold organization-wide credentials.
