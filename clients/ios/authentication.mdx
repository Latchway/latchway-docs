## Outcome

Configure a shared native app, supply an ID token from the application's
existing login flow, and explicitly forward refresh and sign-out. Native or
React Native may configure first; matching settings reuse the same app/account.
There is no Firebase dependency or Latchway authentication bootstrap.

## Keep the boundaries separate

```text
identity token -> identifies the application user
App Attest     -> supplies evidence about the signed Apple application
DPoP proof     -> proves possession of the component session key
feature policy -> decides whether the request may run
```

Configure the server provider first through
[Authentication providers](/clients/authentication-providers). Supply a current
provider ID token; never pass a Latchway access token,
refresh token, App Attest assertion, or provider credential.

## Configure and sign in

```swift
import Foundation
import Latchway
import LatchwayAppAttest

let app = try await LatchwayApp.configure(.init(
    baseURL: URL(string: "https://gateway.example.com")!,
    applicationID: "app_01J00000000000000000000000",
    environment: "development",
    rootKeychainAccessGroup: "YOURTEAM.your.signed.bundle.id",
    suppliedIdentity: try .firebaseProject(projectID: "your-project-id")
))
let account = try await app.signIn { try await yourAuth.currentIDToken() }
let client = try await account.makeClient()
```

`yourAuth` is application code. `firebaseProject` formats public issuer/audience
metadata only: it imports no Firebase and obtains no token. Other supported JWT
issuers use `LatchwaySuppliedIdentityConfiguration(providerID:issuer:audience:tenantID:)`.
The gateway verifies the token; decoded claims are not authenticated identity.
Use the signed private root Keychain group and required App Attest configuration.

Already-signed-in native/RN surfaces can use `try await app.makeClient()` without
another sign-in. Configuration does not reactivate a logged-out account.
Initial auth restoration uses `app.restore`; it cannot undo recorded logout.

## Session and sign-out behavior

```swift
// Same-account provider token refresh:
try await account.updateIdToken { try await yourAuth.currentIDToken() }

// In the application's serialized sign-out flow:
try await app.signOut()
try yourAuth.signOut()
```

Tokens stay in native process memory, not Keychain. Expiry suspends protected
work until a verified same-account update; it is not logout. Supply a token
again after process restart. The SDK cannot observe unreported provider logout.

App sign-out is offline-capable shared native/RN retirement. It cancels pending
sign-in, clears account credentials and retries interrupted cleanup. It does
not reset user quotas, erase every installation key, sign out the identity
provider or affect other devices. Do not swallow secure-storage errors or start
another login until cleanup succeeds. Cancel application-owned tools/streams
and clear old-account UI separately. Closing a client is not sign-out.

Delayed work belonging to an old account should use that captured
`account.logout()`; it cannot retire a newer login. Version 2 removes callback
authorities and automatic legacy storage adoption. See
[release boundaries](/release-status#upgrade-and-rollback).

## Verify

Complete one request and confirm the request view shows a normalized `usr_...`
identity and a separate App Attest trust result. If identity fails, follow the
exact stable code in [Error reference](/reference/errors); do not weaken App
Attest or DPoP while diagnosing authentication.
