## Outcome

A normal `URLRequest` reaches an allowed Latchway data-plane path with a fresh
request-time DPoP proof and one server-owned feature decision.

Keep these invariants when adapting it:

- use the generated `app_...` application resource ID rather than a bundle ID
  or display name;
- target the exact configured HTTPS gateway origin;
- bind the transport to a stable feature such as `habit-assistant`;
- allow Latchway to rewrite the physical model under active configuration;
- never add an upstream provider authorization header or credential-shaped
  query parameter; and
- preserve the response request ID for correlation.

## Choose the transport level

Use the feature transport for ordinary buffered or streamed URLSession work.
Use lower-level `authorize` only when the caller-owned transport can verify the
exact destination and implement the documented one-time pre-dispatch recovery
contract. A copied static authorization header is not a substitute for DPoP.

## Verify

Confirm one request row has the same response request ID, `Platform: ios`, the
expected feature and user, a directly trusted root component, and authoritative
usage. The provider, physical model, price, and usage shown in that row are
server results rather than client assertions.

delivery and cancellation.
