## Outcome

The native adapter submits a Play Integrity Standard token whose `requestHash`
is the server-provided Latchway challenge hash, and the gateway validates the
configured application and verdict expectations.

## Distinguish the three modes

| Mode | What it tests | What it cannot prove |
| --- | --- | --- |
| Local development | Kotlin lifecycle, fixtures, request binding, error mapping | A real Play verdict |
| Google Play Console test response | Real API transport and application handling of configured verdicts | Genuine app recognition, licensing, or device trust |
| Play internal testing | Exact signed candidate installed from a configured track | Production rollout status |
| Production distribution | Released signing and policy coordinates | That the device or app is free from compromise |

## Match exact coordinates

Configure the same values in the Android candidate and active Latchway policy:

- numeric Google Cloud project number;
- package name;
- expected installed signing-certificate digest;
- application recognition verdict;
- version constraints when policy uses them;
- device integrity and account licensing requirements; and
- feature trust requirement.

Pass the server's `client_data_hash` directly as Play Integrity `requestHash`.
Do not hash it again or reconstruct principal-bound JSON on the client.

## Explicit Development testing

<Note>
Development-only acceptance of verified Google testing responses requires server
1.1.3 or later. Upgrade before enabling this policy. Existing environments are
not changed automatically.
</Note>

In Google Play Console, open **Protected with Play → Play Integrity API →
Manage → Testing**. Configure dedicated tester Google accounts and the desired
verdicts. The account is the one used by Google Play on the device, not necessarily
the account used for Firebase authentication. Google marks the response with
`testingDetails.isTestingResponse: true`.
[Google's testing documentation](https://developer.android.com/google/play/integrity/additional-tools)

In the matching Latchway **Development** environment, explicitly set
`playIntegrity.allowTestingResponses: true` on each applicable Android platform
selection. Keep `minimumTrustLevel` at `device_verified` or
`strong_device_verified` and keep the corresponding device-verdict requirements.
Testing responses retain `debug` trust: a narrowly scoped server policy permits
them without upgrading their trust. Generic debug-provider evidence does not gain
this exception. Staging and Production reject this setting even with
`dangerousAllowInProduction`.

The verifier still checks the Google-decoded payload, request hash, freshness,
package, signing certificate, version constraints, app recognition, and configured
licensing/device verdicts. Set successful test verdicts to satisfy those checks,
including `PLAY_RECOGNIZED` and, when required, `LICENSED`. A debug APK with a
different package or certificate is not automatically accepted. Confirm the
installed build's actual values and allowlist only intended development identities.
Google's test-account and release-track prerequisites still apply; test the exact
locally installed build before relying on this workflow.

Native Android and React Native pass the Development cloud project number through
their existing configuration. Native and React Native callers sharing an app must
agree on that value. No debug token, client trust flag, Firebase SDK dependency, or
new bootstrap is needed. Restart the native process after changing its registered
configuration. Google Play testing overrides are app/tester settings: do not assume
a different Cloud project isolates them from production builds.

Turning testing acceptance off prevents renewal/access under the scoped exception.
It does not convert old test evidence into genuine device verification. Re-attest
using real accepted evidence, and keep Production testing acceptance disabled.
After any configuration activation, Play Integrity session renewal conservatively
requires fresh evidence for the new revision. Same-revision renewal is unchanged;
applications should allow the SDK to re-establish attestation.

## Run the protected path

1. warm the Standard token provider;
2. install the exact signed application from the configured track;
3. establish a fresh Latchway session;
4. send one feature-bound request; and
5. inspect the attestation event and request by safe ID.

The adapter may renew an invalid provider once and retry only documented
transient provider failures within its bounded policy. Permanent verdict
failure is a policy result, not a retry loop.
