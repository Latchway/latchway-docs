**Expected time:** 15 minutes after the mandatory gateway, identity, Android
application, and Play prerequisites below are available.

**Mode:** Developer-supplied identity with native Play Integrity. Production
distribution verification remains separate from compilation and testing verdicts.

**Coordinates:** server `1.1.3`; client contract `1.1.0`; Android SDK `1.2.1`.

## Outcome

Send and incrementally consume an OkHttp request for `habit-assistant` through
Android Keystore-backed DPoP, then correlate its safe request ID with the Play
Integrity result and metered usage.

## Before you start

- a configured HTTPS gateway, reachable from the device, that passed the
  [operator quickstart](/operate/quickstart)
- an Android application resource ID, environment, feature, identity policy,
  Play cloud project, package, and certificate digest configured in Latchway
- an existing authentication flow that supplies a current ID token
- Android Studio, minimum runtime API 23, and compile SDK 34 or newer
- for a real verdict, the exact signed application installed from a configured
  Google Play internal or production track

<Warning>
  A fixture, emulator, or sideloaded APK does not prove production Play
  distribution. Development-only testing responses require explicit server
  policy and remain debug trust; they are not device-verification evidence.
</Warning>

## Procedure

<Steps>
  <Step title="Install the shared-account modules">
    Add `google()` and `mavenCentral()` to your dependency repositories, then
    add these dependencies to the application:

```kotlin
dependencies {
    implementation(platform("dev.latchway:latchway-bom:1.2.1"))
    implementation("dev.latchway:latchway-okhttp")
}
```

    This path includes the native Play Integrity integration without Firebase.
    The libraries support runtime API 23 and compile SDK 34; other host
    dependencies may require a higher compile SDK.
    Expected result: all Latchway modules resolve to `1.2.1`.
    Diagnostic: inspect `./gradlew :app:dependencies --configuration debugRuntimeClasspath`
    for mismatched module versions or missing repositories.
  </Step>
  <Step title="Configure and supply your existing user's token">
    Run the sign-in operation from your serialized application authentication
    flow, not from an independent listener in each screen:

```kotlin
import dev.latchway.core.firebaseProject
import dev.latchway.okhttp.LatchwayAppOptions
import dev.latchway.okhttp.LatchwayAppRegistry
import okhttp3.HttpUrl.Companion.toHttpUrl

val app = LatchwayAppRegistry.configure(applicationContext, LatchwayAppOptions(
    baseUrl = "https://gateway.example.com/".toHttpUrl(),
    applicationId = "app_01J00000000000000000000000",
    environment = "development",
    identity = firebaseProject("your-project-id"),
    playIntegrityCloudProjectNumber = 123456789012L,
))
val account = app.signIn { yourAuth.getIdToken() }
val client = account.makeClient()
val http = client.buildOkHttpClient()
```

    `yourAuth` is your existing token-producing application code. The
    `firebaseProject` helper only derives public issuer/audience metadata; it
    does not fetch or authenticate tokens and adds no Firebase dependency.
    Other supported issuers use `LatchwayIdentityConfiguration` directly.
    The gateway authenticates the token. The Play project number is independent
    of your Firebase project and must match this environment's server policy.

    Equivalent native and React Native configuration joins the same app;
    conflicting explicit settings fail. A second caller can use
    `app.makeClient()` to attach without signing in again.

    Expected result: sign-in returns an account after identity and configured
    Play Integrity policy pass. Diagnostic: compare the gateway, application,
    environment, issuer, package, signing certificate, and Play project before
    retrying a stable configuration or attestation error.
  </Step>
  <Step title="Use the protected OkHttp transport">
    Use `http` for your gateway requests and bind each request to the configured
    feature with `Request.Builder().latchwayFeature("habit-assistant")`.
    Add the ordinary JSON body and method required by the endpoint. Keep the
    returned OkHttp `Call`, cancel it when its owner is cancelled, and consume
    streaming responses incrementally. Do not replace the protected transport
    with a separate bare OkHttp client or enable cross-origin redirects.

    Supply refreshed tokens for the same account and await sign-out before a
    new login:

```kotlin
account.updateIdToken { yourAuth.getIdToken() }
app.signOut()
// Your application signs out its external authentication provider separately.
```

    `signOut()` retires the shared native/React Native account locally; it does
    not revoke the installation or reset per-user quota. If cleanup reports
    `CLEANUP_REQUIRED`, retry the same operation after storage becomes available.
    For delayed callbacks tied to an old login, use the captured account's
    `logout()` rather than signing out whichever account is current.

    Expected result: requests carry the configured feature and successful
    sign-out retires the shared account. Diagnostic: correlate the stable error
    code and response request ID; supply a same-account token update when the
    SDK reports that identity refresh is required.
  </Step>
</Steps>

## Optional disposable verification harness

The following generated Firebase example is a separate compatibility/conformance
harness. It still uses the supported direct constructor and optional
`latchway-firebase-auth` adapter, not the shared-account path above. Firebase is
required by this harness only. Do not add it to a new supplied-identity
integration. Its successful journey revokes the test installation and signs out
Firebase; those are deliberate test teardown actions, not ordinary logout.

<Steps>
  <Step title="Prepare the version-matched harness">
    Use the example source from tag `v1.2.1`. Configure its dependency repositories:

```kotlin
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
    }
}

rootProject.name = "habit-assistant-android"
include(":app")
```

    In `app/build.gradle.kts`, add the optional Firebase adapter and dependencies
    because this complete harness uses them directly:

```kotlin
dependencies {
    implementation(platform("dev.latchway:latchway-bom:1.2.1"))
    implementation("dev.latchway:latchway-okhttp")
    implementation("dev.latchway:latchway-play-integrity")
    implementation("dev.latchway:latchway-firebase-auth")

    implementation(platform("com.google.firebase:firebase-bom:34.18.0"))
    implementation("com.google.firebase:firebase-auth")
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-android:1.11.0")
}
```

    Expected result: Gradle resolves `dev.latchway` 1.2.1 from Maven Central.
    Set the app's minimum API to 23 and compile SDK to at least 34; the Firebase
    dependencies may impose their own higher requirements. Diagnostic: run
    `./gradlew :app:dependencies --configuration debugRuntimeClasspath` and
    confirm that all Latchway modules resolve to one version.
  </Step>
  <Step title="Provide the safe deployment coordinates">
    Put the operator-provided, non-secret values in your private user-level
    `~/.gradle/gradle.properties`. Do not commit an identity token, integrity
    token, provider credential, or signing material.

```properties
latchway.gatewayUrl=https://gateway.example.com/
latchway.applicationId=app_01J00000000000000000000000
latchway.environment=production
latchway.feature=habit-assistant
latchway.model=assistant-default
latchway.cloudProjectNumber=123456789012
```

    The gateway must be HTTPS with a trailing slash. `applicationId` is the
    exact `app_...` resource ID, and `cloudProjectNumber` is the numeric Google
    Cloud project configured on both sides. `model` is the request value
    accepted by the feature; the server still owns the physical upstream,
    route, model mapping, pricing, and limits.

    In the `defaultConfig` block of `app/build.gradle.kts`, expose only those
    values as manifest placeholders:

```kotlin
manifestPlaceholders["latchwayGatewayUrl"] =
    providers.gradleProperty("latchway.gatewayUrl").get()
manifestPlaceholders["latchwayApplicationId"] =
    providers.gradleProperty("latchway.applicationId").get()
manifestPlaceholders["latchwayEnvironment"] =
    providers.gradleProperty("latchway.environment").get()
manifestPlaceholders["latchwayFeature"] =
    providers.gradleProperty("latchway.feature").get()
manifestPlaceholders["latchwayModel"] =
    providers.gradleProperty("latchway.model").get()
manifestPlaceholders["latchwayCloudProjectNumber"] =
    providers.gradleProperty("latchway.cloudProjectNumber").get()
```

    Expected result: the app build has six non-secret, environment-specific
    coordinates without embedding any authentication or attestation evidence.
    Diagnostic: `FAIL configuration` means the example rejected a missing or
    malformed coordinate; do not weaken its HTTPS, resource-ID, identifier, or
    positive-project-number checks.
  </Step>
  <Step title="Declare the application metadata">
    In `app/src/main/AndroidManifest.xml`, keep the Internet permission and map
    the placeholders to the names read by the compiled example. If your
    activity uses another package, replace its class name explicitly.

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
  <uses-permission android:name="android.permission.INTERNET" />
  <application>
    <meta-data android:name="dev.latchway.gatewayUrl"
      android:value="${latchwayGatewayUrl}" />
    <meta-data android:name="dev.latchway.applicationId"
      android:value="${latchwayApplicationId}" />
    <meta-data android:name="dev.latchway.environment"
      android:value="${latchwayEnvironment}" />
    <meta-data android:name="dev.latchway.feature"
      android:value="${latchwayFeature}" />
    <meta-data android:name="dev.latchway.model"
      android:value="${latchwayModel}" />
    <meta-data android:name="dev.latchway.cloudProjectNumber"
      android:value="${latchwayCloudProjectNumber}" />

    <activity
      android:name="dev.latchway.sample.firebase.MainActivity"
      android:exported="true">
      <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
      </intent-filter>
    </activity>
  </application>
</manifest>
```

    Expected result: the merged manifest contains the six expected values and
    the launcher activity. Diagnostic: run
    `./gradlew :app:processDebugMainManifest` to distinguish manifest merging
    from Kotlin, Firebase, signing, or runtime policy failures.
  </Step>
  <Step title="Add the compiled client and streaming flow">
    Put the following complete source in
    `app/src/main/kotlin/dev/latchway/sample/firebase/MainActivity.kt`, or
    change its first `package` declaration and the manifest activity name to
    match your application. This region is generated from the SDK's compiled
    `sample-firebase` application rather than transcribed pseudocode.

    <AndroidFirebaseGoldenJourney />

    The example uses only public SDK APIs. It constructs
    `FirebaseIdentityTokenProvider`, `PlayIntegrityAttestationProvider`, and
    `LatchwayClient`; installs the application interceptor, network origin
    guard, and bounded authenticator; disables redirect and connection replay;
    binds `habit-assistant` with `latchwayFeature`; retains the OkHttp `Call`;
    cancels it with the owning coroutine; reads the response incrementally with
    a one MiB example bound; and reports only typed errors and safe request IDs.

    Expected result: `./gradlew :app:compileDebugKotlin` compiles the complete
    send, streaming, cancellation, diagnostics, quota, and cleanup flow.
    Diagnostic: run
    `../latchway-android/gradlew -p ../latchway-android :sample-firebase:compileDebugKotlin`
    to separate SDK/source drift from application build configuration.
  </Step>
  <Step title="Run the one-shot golden journey">
    Sign in through the application's normal Firebase flow. For a real Play
    verdict, install the exact signed build from the configured internal or
    production Play track, open it, and tap **Run golden journey**.

    The harness consumes stream bytes as they arrive; it does not call
    `string()` or buffer an unbounded success body. Destroying the activity
    cancels its coroutine and the retained OkHttp call. A successful evidence
    run intentionally revokes the test installation and signs out Firebase, so
    move those lifecycle actions out of the ordinary request path when adapting
    this harness for a long-lived application.

```text
PASS · response req_... · diagnostics req_... · quota 3 limits · installation revoked · Firebase signed out
```

    Expected result: the status begins with `PASS` and includes a safe response
    request ID. Use the ID after `response`, not the later diagnostics request
    ID, for request-row correlation. Diagnostic: a `FAIL` status contains only
    its stage, stable Latchway code or HTTP status, documentation URL, and safe
    request ID; follow those fields instead of logging tokens or verdicts.
  </Step>
  <Step title="Verify the response in the Console">
    Open **Requests**, filter by `habit-assistant`, and correlate the response

    Expected result: exactly one response request row has the same request ID

## Troubleshooting

<AccordionGroup>
  <Accordion title="Play Integrity rejects the application">
    Compare the numeric cloud project, package, certificate digest, release
    track, and server environment. A locally installed build may not receive
    the verdict required by production policy. Continue with
    [Play Integrity](/clients/android/play-integrity) without copying an
    integrity token into logs or source.
  </Accordion>
  <Accordion title="The example reports FAIL configuration or FAIL Firebase">
    For configuration, verify all six safe properties, the HTTPS trailing
    slash, canonical `app_...` resource ID, identifiers, and positive project
    number. For Firebase, initialize the configured application and sign in
    through its normal UI before running. Never paste an ID token into a
    property or diagnostic output.
  </Accordion>
  <Accordion title="The request is redirected or receives a stable error">
    A redirect failure is intentional: configure the final exact HTTPS gateway
    origin and never allow DPoP or authorization headers to cross origins. For
    a stable error, open [Errors](/reference/errors), correlate its safe request
    ID, and inspect trust, feature grant, and reserved quota.
  </Accordion>
</AccordionGroup>
