**Expected time:** 15 minutes after gateway resources, application login and
native signing are configured. This guide targets server 1.1.3, React Native
SDK 2.0.0, iOS SDK 2.0.0 and Android SDK 1.2.1. Check
[Release status](/release-status) for package availability; a prepared source
release does not itself establish publication or physical-device acceptance.

**Mode:** Application integration, standalone or embedded React Native.

**Coordinates:** server `1.1.3`, contract `1.1.0`, wire `3`; React Native `2.0.0`,
iOS `2.0.0`, Android `1.2.1` and JavaScript client `1.1.0`.

## Outcome

Configure Latchway from React Native, supply a current identity token from your
existing login flow, and send one Chat Completions request to `habit-assistant`.
Find its request ID and usage in the Console. The same setup works in a
standalone app or a React Native screen embedded in a native app.

Either native or React Native can configure first. Equivalent configuration
reuses one native app, account and session. You do not need a native Latchway
bootstrap, Firebase dependency, or separate embedded-mode setting.

## Before you start

- A reachable server 1.1.3 gateway with an application resource ID, environment,
  identity provider and `habit-assistant` feature routed to `openai_chat`.
- React Native `>=0.74.0 <1.0.0`, React `^18.2.0 || ^19.0.0`, and the New
  Architecture. Use a compatible React/React Native pair for your host.
- An application login flow that can return a current user ID token accepted
  by the gateway. A project ID alone is not authentication.
- A signed iOS 15+ app with App Attest and the private root Keychain group, or
  an Android API 24+ app with Play Integrity configured for its package and
  signing certificate. Complete both hosts when shipping both platforms.
- An explicit gateway `sharedNativeCallers` policy permitting the intended
  native and React Native callers, with the required host attestation unchanged.

Never put upstream provider keys, service-account JSON, App Check tokens or
admin credentials into this client. The application resource ID (`app_...`) is
not a Firebase app ID, bundle identifier or Android package name.

## What you will build

```text
Application login -> shared native account -> feature-bound request -> Console usage
```

Authentication belongs to your app. Native modules own keys, attestation, DPoP,
session credentials and networking; the gateway owns routing and quota.

## Procedure

<Steps>
  <Step title="Install and rebuild the native host">

```bash
npm install --save-exact @latchway/react-native@2.0.0
cd ios
pod install
cd ..
```

    CocoaPods resolves `Latchway/AppAttest` 2.0.0; Android resolves the locked
    `dev.latchway` 1.2.1 modules from Maven Central. Retain the lockfiles and
    rebuild the native application. Do not add a second native SDK copy or
    local source override in a registry-based integration.

    Follow [iOS host setup](/clients/react-native/ios-native-setup) or
    [Android host setup](/clients/react-native/android-native-setup). Android
    libraries compile against API 34; your host or other dependencies may
    require a newer compile or target SDK. Simulator or emulator compilation
    does not establish a physical App Attest or Play Integrity verdict.

    Expected result: npm and native dependency locks resolve the listed versions
    and the host compiles. Diagnostic: inspect `Podfile.lock` or Gradle dependency
    output for duplicate Latchway copies; a JavaScript reload cannot update native code.

  </Step>
  <Step title="Configure public app and identity metadata">

    Put this in an application service module. Replace the public coordinates
    with values from your own gateway and signed app:

```ts
import {Latchway, firebaseProject} from '@latchway/react-native';

export const configuredApp = Latchway.configure({
  baseURL: 'https://gateway.example.com',
  applicationID: 'app_01J00000000000000000000000',
  environment: 'development',
  identity: firebaseProject({projectID: 'your-project-id'}),
  apple: {rootKeychainAccessGroup: 'YOUR_SIGNED_ROOT_KEYCHAIN_GROUP'},
  android: {playIntegrityCloudProjectNumber: '123456789012'},
});
```

    `firebaseProject` formats issuer/audience metadata only. It imports no
    Firebase module, acquires no token and installs no listener. Other
    gateway-supported JWT providers use
    `identity: {providerID, issuer, audience, tenantID?}`. The gateway must have
    the matching verifier configured.

    Use the actual signed private root Keychain group, not an unresolved Xcode
    expression or a guessed Team ID and bundle combination. Matching native
    and React Native configurations reuse the same app. Conflicting explicit
    values fail with `configuration_conflict`; configure never signs in or
    reactivates a logged-out account.

    Expected result: configuration returns the shared app handle regardless of
    which caller configured first. Diagnostic: compare explicit coordinates on
    `configuration_conflict`, including the actual signed Keychain group.

  </Step>
  <Step title="Supply identity after an accepted login">

```ts
const app = await configuredApp;
const account = await app.signIn({
  getIdToken: () => yourAuth.getIdToken(),
});
const client = await account.makeClient();
const assistantFetch = client.fetchFor('habit-assistant');
```

    `yourAuth` is your application-owned authentication integration. Its getter
    returns a current user ID token. Latchway invokes it once after capturing
    the native operation; it is not retained as a permanent JS auth owner.
    Already acquired tokens can use `app.signIn({idToken})`.

    If another native or React Native caller already signed in, attach with
    `await app.makeClient()` instead. Initial application-auth restoration uses
    `app.restore({getIdToken})`; it cannot reverse a recorded Latchway logout.
    A screen mounting is not a new login.

    Expected result: a verified account returns a native-backed client without
    exposing session credentials. Diagnostic: check the gateway identity provider
    and current token's source on identity rejection; never print the token.

  </Step>
  <Step title="Send one request and retain its safe request ID">

```ts
import {errorFromResponse} from '@latchway/react-native';

const controller = new AbortController();
const response = await assistantFetch('/v1/chat/completions', {
  method: 'POST',
  signal: controller.signal,
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({
    model: 'latchway',
    messages: [{role: 'user', content: 'Suggest one small habit for tomorrow.'}],
    max_tokens: 256,
    stream: false,
  }),
});
if (!response.ok) throw await errorFromResponse(response);

const requestID = response.headers.get('X-Latchway-Request-ID');
const answer = await response.json();
// Render answer.choices[0].message.content in your app and show requestID.
// Do not log the token, request body, response body or native proof material.
```

    The model value is a compatibility placeholder. The feature's active route
    owns the upstream and physical model. Use `/v1/responses` only with a
    separately configured Responses feature and its matching request body.
    Every model round consumes configured quota, including tool rounds.

    Connect the controller to your screen's Stop action, teardown and account
    changes. Cancellation does not authorize retrying an uncertain provider
    dispatch. For streaming and tools, continue with the
    [LangChain integration](/clients/react-native/framework-integrations).

    Expected result: the response contains an assistant message and a safe
    request ID. Diagnostic: match that ID to the Console row and confirm the
    feature uses `openai_chat`; a Responses feature needs its own request shape.

  </Step>
  <Step title="Wire token refresh and shared logout">

```ts
// On a same-account token refresh:
await account.updateIdToken({getIdToken: () => yourAuth.getIdToken()});

// On logout, in your serialized application auth flow:
controller.abort();
await app.signOut();
await yourAuth.signOut();

// Screen teardown alone releases a client, not the shared account:
await client.dispose();
```

    Tokens remain only in native process memory. When supplied identity
    expires, `identity_refresh_required` suspends protected work until a
    verified same-account update. After process restart, application auth
    supplies a token again. Latchway cannot discover an external-provider
    logout that the application never reported.

    Logout is shared by native and React Native and works offline. It does
    not reset server-side user quotas, revoke the whole installation or log
    out other devices. App sign-out cancels pending sign-in; also cancel old
    streams/tools, and clear in-memory chat on account changes. See
    [authentication](/clients/react-native/authentication) for restoration,
    cancellation and an optional provider-neutral event binding.

    Expected result: same-account refresh resumes suspended work, and logout
    blocks old native/RN clients. Diagnostic: confirm every application auth
    surface reports changes; disposing a client is not a logout operation.

  </Step>
</Steps>

## Verification

Run the request on each platform you ship. Correlate the returned request ID
with one successful Console row: expected environment, feature, normalized
user, native host, React Native caller, required attestation, DPoP and token
usage. Test native-first and RN-first configuration, same-user token refresh,
expiry/recovery, logout and switching accounts.

Fresh source tests or package publication do not replace physical acceptance.
For iOS, verify the exact signing and App Attest environment. For Android,
verify the Play-distributed build on a physical device; a sideloaded Debug APK
is not production Play Integrity evidence.

## Troubleshooting

- `configuration_conflict`: compare explicit native/RN app name, origin,
  environment, identity metadata and signed security coordinates.
- `identity_refresh_required`: obtain a current ID token through application
  auth and update the captured account; do not disable identity verification.
- Missing server capability: confirm server 1.1.1 advertises
  `supplied_identity_v1`. An SDK upgrade alone cannot add server capabilities.
- Native module unavailable: rebuild with the New Architecture and inspect
  the [installation](/clients/react-native/installation) dependency locks.
- Attestation denied: inspect the safe request ID in the Console and compare
  the signed app with the gateway policy. Do not substitute a development
  bypass for production App Attest or Play Integrity.
