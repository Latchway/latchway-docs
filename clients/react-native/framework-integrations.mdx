## Outcome

A tested framework consumes `fetchFor(feature)` while native modules retain
DPoP, attestation, session state, destination validation, and response
streaming.

## Start from generated evidence

For a current LangChain application, use the published setup below. Generated
framework tables retain their historical conformance coordinates; they are not
evidence of fresh physical-device testing for these package versions.

Use [React Native framework integration](/integrations/react-native) and the
generated [Compatibility matrix](/reference/compatibility) for exact package
versions and covered capabilities. The source candidate includes consumers for
selected OpenAI JavaScript, Vercel AI, LangChain JavaScript, and Anthropic
Messages paths.

This is not a blanket claim for every API in those packages. Browser-only
middleware, Node filesystem dependencies, service workers, Realtime, uploads,
audio, images, streaming request bodies, or framework paths without a custom
fetch seam remain outside the tested surface.

## Install LangChain in the host app

```bash
npm install --save-exact @latchway/react-native@1.1.2 @latchway/langchain@1.1.0 \
  @latchway/client@1.0.0 @langchain/core@1.2.9 @langchain/openai@1.5.10 openai@7.8.0
```

The base SDK does not depend on LangChain, Babel helpers or global URL/decoder
polyfills. Follow the versioned
[runtime and Babel guide](https://github.com/Latchway/latchway-react-native-sdk/blob/v1.1.2/docs/langchain.md)
and copy its application-owned bootstrap before importing frameworks. Reuse
complete globals already supplied by the host; do not install duplicate native
randomness modules or replace global fetch. Recopy old bootstrap files when
upgrading: npm cannot update copies in application source.

React Native's partial URL implementation can add a trailing slash to an API
path. Version 1.1.2 checks exact Chat Completions and Responses paths and preserves
working host implementations. Never widen the SDK destination allowlist to hide
`transport_destination_not_allowed`.

## Create a Chat Completions model

After native setup and Firebase/other user login, pass the client directly:

```ts
import {createLatchwayChatOpenAI} from '@latchway/langchain';

const model = createLatchwayChatOpenAI({
  latchway,
  feature: 'assistant-chat',
  chatOptions: {maxTokens: 1024, maxRetries: 0},
});
const controller = new AbortController();
for await (const chunk of await model.stream('Help me plan tomorrow.', {
  signal: controller.signal,
})) {
  // Render incremental text without storing credentials or incomplete history.
}
```

The feature must select `openai_chat`. For an `openai_responses` feature use
`createLatchwayResponsesModel` on server 1.0.2+, with model-appropriate generation
options and accounting. The server chooses the physical model; no upstream key
belongs in either constructor. Defaults disable framework retries; preserve
cancellation and never replay an uncertain dispatch automatically.

Scope the client and in-memory history to the signed-in user and environment.
On account change, abort work, ignore stale callbacks, clear history and dispose
the old client. Use the user's Firebase ID token, not a UID, App Check token,
custom sign-in token or service-account JSON. Read authoritative quota from the
server. Tool execution remains app-owned: validate arguments, enforce an
allowlist, bound the loop and append complete correlated tool results only.

## Bind each protocol separately

Create a separate feature for Responses, Chat Completions, Embeddings,
Anthropic Messages, or an allowed opaque route. One feature cannot represent
multiple protocol adapters. Give the framework a fetch permanently bound to
that feature and the canonical gateway origin.

Use a conspicuous non-secret placeholder only when a constructor requires an
API-key-shaped value. Native filtering must discard it. Disable
framework-owned retries and preserve `AbortSignal` plus incremental response
consumption.

## Verify
