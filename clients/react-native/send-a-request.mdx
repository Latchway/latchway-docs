## Outcome

JavaScript supplies the application payload and feature while native code
attaches Authorization and DPoP, sends the request, and owns the response
stream.

## Create one stable client

After [configuration and sign-in](/clients/react-native/authentication), create
a client from the captured account:

```ts
const client = await account.makeClient();
const assistantFetch = client.fetchFor('habit-assistant');
```

If another caller already signed in, attach with `app.makeClient()`; do not
start a new login because a screen mounted. At identity expiry, supply a fresh
token through `account.updateIdToken` before resuming protected work.

The generated application resource ID is not a bundle ID, Android package,
display name, or slug. Equivalent native and RN callers share one app/account;
retain a client for its owning screen or operation and dispose it on teardown.
Disposing the client does not log out the shared account.

Use `fetchFor(feature)` when adapting a framework. The client supports the
contract-owned structured POST paths and explicitly configured safe opaque
routes. It rejects a cross-origin destination, redirect, traversal-shaped
path, fragment, unsafe query, forbidden credential header, streaming request
body, or request body larger than the bridge limit.

The model-shaped value required by some frameworks is a compatibility input;
the server-selected route and physical model remain authoritative.

## Verify

Confirm the response request ID matches one Console row with the expected
`react_native_ios` or `react_native_android` platform, normalized user, family,
component, feature, native trust, DPoP result, route, and usage. JavaScript
diagnostics must contain none of the native credentials or raw evidence.

Continue with [Streaming](/clients/react-native/streaming) for backpressure and
cancellation behavior.
