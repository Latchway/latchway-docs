The embedded console is a same-origin client of the canonical Admin API. It
does not connect directly to PostgreSQL, evaluate policy in the browser, keep
credentials in Web Storage, or maintain a second configuration model.

## Authentication

The first owner consumes the one-time bootstrap token. After that, bootstrap is
permanently closed and administrators sign in with a secure same-origin cookie
session. Mutations require both a validated Origin and the session-bound CSRF
token.

API automation uses scoped, expirable, revocable bearer tokens instead. A token
cannot exceed its owner's current organization role or its explicit scopes.

| Capability | Typical use |
| --- | --- |
| `manage_owners` | Administrator membership and owner lifecycle |
| `manage_secrets` | Create, rotate, and retire write-only secrets |
| `activate_configuration` | Create tenant resources and activate configuration |
| `run_self_tests` | Immediate and scheduled bounded verification |
| `inspect_users` | Users, installations, requests, usage, and audit views |
| `revoke_installations` | Block users and revoke installations |
| `view_prompt_bodies` | Reserved capability; v1 rejects body storage and exposes no body-read endpoint |

Resource editors clone the complete active document, replace only the selected
resource wrapper, preserve every other parsed value, and submit the full draft
under its ETag. The server remains authoritative for validation, planning,
simulation, activation, tenancy, and auditing.

## Live operational refresh

Servers that negotiate `admin_event_stream` expose a same-origin Server-Sent
Events channel. It sends only closed topic hints for requests, usage,
configuration, audit, self-tests, and health. The console then reloads the
visible view through its canonical bounded endpoint. The stream never includes
resource identifiers, user data, counts, request content, credentials, proofs,
or provider errors.

Each connection closes within one minute so reconnecting reauthenticates the
administrator session and bounds revocation latency. Reconnect always reloads
canonical state; event IDs are not a durable replay log. A compatible older
server without this optional capability uses a bounded foreground refresh
fallback instead of failing the console compatibility check.

## Application and environment lifecycle

Applications and environments expose explicit active/disabled state. Disable
requires `activate_configuration`, a bounded reason, and an acknowledgement of
the immediate credential effect. The server changes status and transactionally
revokes active legacy and component session/refresh credentials in the exact
scope. Disabling an application preserves each child environment's own status.

Enabling restores only future eligibility. It never restores a revoked access
grant, refresh token, rotation result, or component-session family. The console
keeps disabled scopes selectable for authorized forensic request, usage, audit,
user, installation-family, and configuration-history inspection, but disables
configuration mutation. The server independently enforces the same boundary.

## Secrets

Secret lists show only metadata. Create and rotate inputs are password fields;
the browser clears plaintext before the request completes and the server never
returns it. Deletion displays the exact current secret version, explains the
permanent name tombstone, requires the operator to type the logical name, and
rechecks the name-to-ID binding before sending the mutation.

A referenced, stale, superseded, or cross-tenant secret cannot be deleted.

## Users and installations

User records use opaque IDs and safe normalized claims rather than raw external
subjects. Blocking a user prevents future sessions and revokes current grants
and refresh state. Unblocking permits a future enrollment but never restores a
revoked credential.

Installation revocation destroys that installation's sessions and rotating
refresh family. Record an operator-approved reason without including identity
tokens or incident secrets.

## Scheduled self-test exception

Creating a durable self-test schedule cannot use a browser cookie as future
execution authority. The operator supplies an existing `run_self_tests` token
in a password field for one request. The console sends only that bearer with
cookies omitted, does not add CSRF, clears the field, and persists only the
stable token ID returned by the server.

## Strong client boundary

Console response schemas are strict and bounded. An unknown response field,
including an accidentally returned secret value, fails closed. Request details
show ordered attempts and safe provenance, never provider bodies, internal
errors, identity subjects, proofs, or credentials.

Use [Configuration](/administration/configuration) for the revision lifecycle
and [Operational views](/administration/observability) for requests, usage,
audit, and system status.
