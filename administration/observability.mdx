The console, CLI, and Admin API expose tenant-scoped operational state without
returning provider credentials, raw identity subjects, bearer or refresh
tokens, DPoP proofs, attestation evidence, provider error bodies, or request
content by default.

## Users and installations

Users are pseudonymous within the organization and environment. Operators can
inspect safe normalized claims, block or unblock a user, and apply or clear one
bounded limit-plan override. An override cannot change feature access or route
selection.

Installations expose platform, normalized trust, lifecycle, and safe diagnostic
metadata. Revocation invalidates grants and refresh state; it does not reveal
the installation key or attestation object.

## Requests and attempts

One logical request represents one client operation. Its detail view includes:

- lifecycle status, start, completion, and duration;
- aggregate normalized usage and integer nano-USD cost;
- ordered physical attempts numbered 1 through 32;
- selected route, upstream alias, physical model alias, and safe HTTP status;
- start, optional first-byte, optional protocol-validated first-token, and
  optional completion timing;
- a closed failure category;
- independent token-usage and cost provenance.

Fallback does not double-count the logical request. The public attempt failure
vocabulary is `canceled`, `gateway_error`, `protocol_error`, `timeout`,
`unavailable`, `upstream_rejected`, and `unknown`. Unknown durable values are
collapsed to `unknown` rather than rendered as internal text.

## Usage and analytics

Usage summaries aggregate in PostgreSQL before bounded results are returned.
They can include requests, active users, input/output/total tokens, integer
nano-USD cost, request and first-token latency, failures, quota denials,
attestation failures, fallback rates, and bounded feature/model/plan breakdowns.
First-token latency includes only attempts where a structured protocol observed
generated content. Lifecycle-only, opaque, and historical attempts remain
absent rather than falling back to first-byte latency.

Estimated, calculated, provider-reported, and unknown provenance remain
separate. A provider-reported OpenRouter cost is explicitly labeled
`openrouter_usage_cost`; it is not confused with configured catalog cost.

Summary ranges are half-open and limited to 366 days. Timeseries use UTC hours
or days and cannot exceed 10,000 points. Collection pages use opaque keyset
cursors with at most 200 rows; pass a returned cursor back unchanged.

```bash
latchway requests list --environment env_...
latchway requests inspect req_...
latchway usage summary --environment env_...
latchway usage timeseries --environment env_... --interval hour
```

## Audit history

Audit events are append-only, tenant-scoped, and redaction-safe. They contain
opaque actor and target IDs plus ordered field, operation, and classification
markers. They do not contain before/after values, free-form mutation reasons,
passwords, tokens, secret values, or request bodies. Lists support exact actor
kind/ID, action, resource type/ID, environment, descriptive source, stable
reason code, outcome, and time filters; detail preserves the same value-free
contract.

```bash
latchway audit --organization org_...
latchway audit --organization org_... --environment env_... --source cli
latchway audit inspect aud_...
```

`console` is derived from authenticated session transport and `system` is
server-owned. `cli` versus `api` is a bounded client claim by an authenticated
API token. Treat it as descriptive metadata, never authorization evidence.

If a mutation returns `operation_indeterminate`, preserve its operation ID and
request ID and reconcile the audit record before deciding whether to retry.

## System health

`GET /admin/v1/system` and `latchway status` report build, contract, protocol,
process role, migration version, and readiness. Dependency detail is reduced to
a readiness bit; database addresses and raw errors are not returned.

The Console Health center, `GET /admin/v1/system/doctor`, and `latchway doctor`
share one structured check contract for database/schema, active revisions,
keys, JWKS, worker/job state, scheduled connection tests, quota cleanup, clock,
storage, pool pressure, and SDK compatibility. Downloaded support bundles are
structurally allowlisted and exclude credentials, tokens, cookies, proofs,
master-key material, attestation evidence, and request/response content.

Read each check as a bounded observation, not as a broader certification:

| Check | What a pass actually establishes |
| --- | --- |
| `configuration_cache_state` | The API process that produced the report has a bounded, internally consistent cache with no entry beyond its reconciliation interval. A surface without process-local cache access reports `skipped`. |
| `external_jwks_reachability` | Durable identity-provider state includes a recent successful JWKS refresh with no retained bounded error or stale provider. The doctor does not make a live request to the provider. |
| `apple_verification_dependencies` | Active App Attest selections compile and the PostgreSQL-backed registered-key inventory is readable. It does not call Apple or prove a fresh physical-device assertion. |
| `google_verification_dependencies` | Active Play Integrity and Firebase App Check selections compile, and every credential-backed selection resolves to an active server-owned record. It does not call Google or prove a fresh device verdict. |
| `replica_coverage` | Durable heartbeats observed in the last 90 seconds cover the roles required by the diagnostic surface. A worker-only report cannot prove API coverage. |
| `usage_rollup_freshness`, `retention_job_freshness`, and `usage_reconciliation_freshness` | The latest retained successful job falls within its fixed freshness window while a worker heartbeat is fresh. This is job-history evidence, not proof about an arbitrary request. |
| `storage_retention` | Fixed operational retention is being maintained and the oldest retained request, usage, and audit timestamps can be inspected without content. Tenant-data retention remains deployment-policy owned. |
| `sdk_compatibility` | The current binary has complete embedded contract metadata. `latest_compatible_version` uses the `embedded_self` source and is not a registry lookup or remote update claim. |

For process-level metrics, traces, worker jobs, and alerting, continue with
[Telemetry and jobs](/operations/telemetry-and-jobs).
